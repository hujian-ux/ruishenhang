# 技术规格书到需求评估表结构化提取

## 一、这个 Skill 解决什么

投标阶段拆解技术规格书的真实困难，不是「读不懂」，而是**条目散、判定无口径、评估靠个人经验**：

- 一份规格书动辄上百条技术要求，散在系统架构、公文管理、流程审批等多个章节，人工逐份通读后手工摘录成表，跨文档比对时容易遗漏或重复
- 「我们能不能做」没有统一判定标准，同一规格书，两个售前技术岗能评估出两个结论
- 工作量与风险判断依赖个人经验，评审会上各说各话，无法复核
- 成稿后的应答遗漏只能靠人工通读发现

本 Skill 的核心动作，是把「读文档」变成「审表格」：以固定判定口径（符合度四档、风险规则、工作量基准）逐条过规格书条目，每行结论都能回溯到规格书原文与命中的规则。

## 二、什么时候用（适用时机）

| 触发情形 | 说明 |
| --- | --- |
| 拿到客户技术规格书或招标文件技术部分 | 主用场景：条目提取 + 符合度评估 + 工作量与风险初判 |
| 多份规格书需要合并比对去重 | 跨文档条目在同一上下文中提取，统一字段成表 |
| 投标应答前需要逐条核对必选项 | 评估表直接作为应答核对清单，负偏离项提前暴露 |
| 评审会需要一份可复核的需求清单 | 每行评估依据写明规格书定位与命中规则，任何人可复算 |

**不适用**：商务报价测算（评估表不构成报价依据）；中标后的详细实施方案（→ 交付实施类场景）。

## 三、输入（inputs）

| # | 输入文件 | 必需 | 关键字段 |
| --- | --- | --- | --- |
| 1 | `技术规格书要点.csv` | 必需 | 需求编号、所属章节、技术要求描述、必选或可选、规格值或参数 |
| 2 | `评估表框架.md` | 必需 | 符合度四档判定标准、风险等级规则、工作量估算基准（章节基础人日×符合度系数，可选拆八折）、应答策略口径 |

> 缺 2（评估表框架）时，本 Skill **必须拒绝输出**——没有统一判定口径的需求评估表只是个人意见清单，这是本 Skill 最重要的一条硬规则。

## 四、输出（outputs）

唯一交付物：`需求评估表.csv`，字段固定为 10 列：

```
需求编号, 所属章节, 技术要求摘要, 必选或可选, 符合度判定, 实现方式概要,
工作量估算人日, 风险等级, 应答策略, 评估依据
```

- `符合度判定` ∈ {完全符合, 基本符合, 部分符合, 需定制开发}
- `风险等级` ∈ {高, 中, 低}
- `评估依据` 必须同时包含需求定位（REQ-XX 与规格值）与命中规则（档位/系数/基准人日），**不允许写「综合判断」**

## 五、工作流程（workflow）

### STEP 1 · 先立框架，再过条目

从 `评估表框架.md` 读入符合度四档标准、风险规则与工作量基准，写成显式判定表。**顺序不可颠倒**——先看条目再定标准，等于给结论找理由。

### STEP 2 · 条目提取与归一

读入技术规格书要点，按统一字段（章节/要求/必选或可选/规格值）整理成表；多份规格书时在同一上下文中提取、比对、去重，跨文档重复条目合并并在评估依据中注明出处。

### STEP 3 · 逐条符合度判定

按四档标准逐条判定，判定必须落到产品能力事实（标准能力 / 配置启用 / 低代码补齐 / 定制开发），不允许出现无实现方式支撑的档位。

### STEP 4 · 工作量与风险计算

```
工作量人日 = 章节基础人日 × 符合度系数（可选需求再 ×0.8），四舍五入取整，最低 1 人日
```

风险按规则定档：需定制开发且必选 → 高；需定制开发且可选、部分符合 → 中；其余 → 低。

### STEP 5 · 应答策略生成

按「符合度 × 必选/可选」矩阵生成应答策略；**负偏离提示项必须写明补偿措施与工作量**，禁止空应答。

### STEP 6 · 自检与人工边界声明

输出前逐项自检，任一不过则不得输出。

## 六、关键规则（不可协商）

1. **必选项逐条应答。** 18 条必选项不允许合并、省略或「见上文」式引用。
2. **评估依据可回溯。** 每行必须写明 REQ-XX 规格值定位与命中的框架规则；工作量数字任何人按基准可复算。
3. **负偏离必须给补偿。** 需定制开发且必选的条目是投标最大风险源，补偿措施与工作量缺一不可。
4. **评估表不构成报价依据。** 商务报价由商务评审另行确定；工作量估算不含项目管理与联调缓冲。
5. **淘汰与保留同理留痕。** 每条结论都写实现方式概要，供评审会上被质询时直接引用。
6. **不承诺效率百分比。** 输出中不写「提升 X%」这类无法核验的表述。

## 七、人工边界

| AI 负责 | 人负责（售前技术岗 / 商务） |
| --- | --- |
| 条目提取、去重与归一成表 | 产品能力对照表的事实确认 |
| 符合度、工作量、风险的规则化初判 | 定制开发可行性判断与方案裁决 |
| 应答策略与负偏离提示生成 | 商务报价与投标决策 |
| 评估依据留痕 | 跨部门（研发/交付）工作量复核 |

## 八、下游衔接

- 评估表「需定制开发」行 → 移交研发与交付侧做定制可行性确认
- 评估表全部行 → 作为投标应答文件的逐条应答核对清单

## 附 · 执行细则（本案例主提示词约束并入）

以下细则来自本场景案例的主提示词，与上文「关键规则」同等效力，执行时一并遵守。

### 执行要求

【执行要求】
1. 先读 `评估表框架.md` 再看条目：把符合度四档、风险规则、工作量基准写成显式判定表，不要先看条目再定标准。
2. 读入 `技术规格书要点.csv` 22 行，确认字段齐全：需求编号 / 所属章节 / 技术要求描述 / 必选或可选 / 规格值或参数；必选 18 条、可选 4 条，章节覆盖系统架构 4 / 公文管理 3 / 流程审批 3 / 集成接口 4 / 安全合规 3 / 性能要求 2 / 移动应用 3。
3. 逐条判定符合度档位（完全符合 / 基本符合 / 部分符合 / 需定制开发），每条同步给出实现方式概要——档位必须有产品能力事实支撑。
4. 工作量计算：章节基础人日（系统架构 6 / 公文管理 4 / 流程审批 4 / 集成接口 8 / 安全合规 6 / 性能要求 3 / 移动应用 4）× 符合度系数（完全符合 0.5 / 基本符合 1.0 / 部分符合 1.5 / 需定制开发 2.5），可选需求再 ×0.8，四舍五入取整，最低 1 人日。
5. 风险定档：需定制开发且必选 → 高；需定制开发且可选、部分符合 → 中；其余 → 低。
6. 按应答策略口径逐条生成：正向应答 / 正向应答+实现路径说明 / 负偏离提示+补偿措施 / 可选应答+实现建议。

### 硬性约束

【硬性约束】
- 必选项 18 条逐条应答，不允许合并或省略。
- 评估依据不允许写「综合判断」，必须含需求编号定位与命中规则，工作量数字按基准可复算。
- 需定制开发且必选的条目（负偏离提示）必须写明补偿措施与工作量。
- 评估表不构成报价依据；工作量估算不含项目管理与联调缓冲。
- 不写任何效率百分比或效果承诺。

### 生成后自检

【生成后自检，逐条回答】
1. 输出是否为 22 行、10 列，列名与顺序固定？
2. 必选 18 / 可选 4 是否与输入一致？
3. 符合度分布是否为：完全符合 11 / 基本符合 5 / 部分符合 2 / 需定制开发 4？
4. 风险分布是否为：高 3 / 中 3 / 低 16？高风险项是否为 REQ-11 / REQ-14 / REQ-15？
5. 总工作量是否 = 127 人日？高风险 3 项合计是否 = 55 人日（占比 43.3%）？
自检全过再输出 CSV。

### 输出格式

【输出格式】CSV，10 列，列名与顺序固定：
需求编号, 所属章节, 技术要求摘要, 必选或可选, 符合度判定, 实现方式概要, 工作量估算人日, 风险等级, 应答策略, 评估依据
