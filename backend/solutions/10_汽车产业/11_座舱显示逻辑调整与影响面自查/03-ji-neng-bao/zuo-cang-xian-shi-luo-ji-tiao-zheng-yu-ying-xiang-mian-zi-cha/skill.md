# 座舱显示逻辑调整与影响面自查

## 一、这个 Skill 解决什么

显示逻辑调整的真实风险不在「怎么改一行代码」，而在**改之前不知道谁在用这份数据**：

- 仪表上改一个电量显示分支，语音助手的电量查询、中控主页的能耗卡片用的可能是同一个数据能力
- 车型形态与能源形态两个维度叠加，同一个显示项在不同形态下的分支行为很容易改漏
- 显示项改了，但对应数据的更新监听没注册，结果就是「改对了逻辑、显示不刷新」

本 Skill 的核心动作是**先查影响面、再动手**：把「改—测—回退」的循环变成「查—改—核对」。

## 二、什么时候用（适用时机）

| 触发情形 | 说明 |
| --- | --- |
| 需求要求某车型形态展示更多指标 | 主用场景：影响面检索 + 逐项调整方案 + 监听核查 |
| 不确定某个数据能力还有哪些调用方 | 用模块引用关系表先列出引用清单，再决定改不改 |
| 显示结果与预期不符 | 按环节逐层追问定位（配置 → 分支 → 监听 → 数据源） |
| 改动上线前的自查 | 逐项核对监听完整性与需同步调整模块 |

**不适用**：纯视觉样式（颜色、字体、间距）调整；底层驱动与硬件信号问题。

## 三、输入（inputs）

| # | 输入文件 | 必需 | 关键字段 |
| --- | --- | --- | --- |
| 1 | `显示逻辑配置表.csv` | 必需 | 显示项、数据能力、车型形态、能源形态、当前展示逻辑、所属模块、更新监听 |
| 2 | `模块引用关系表.csv` | 必需 | 数据能力、引用模块、调用方式 |

> 缺 2（模块引用关系表）时，本 Skill **必须拒绝输出「需同步调整模块」列**，只能标注「影响面未检索」——这是本 Skill 最重要的一条硬规则。

## 四、输出（outputs）

唯一交付物：`影响面分析与调整方案表.csv`，字段固定为 8 列：

```
显示项, 数据能力, 车型形态, 是否需调整, 影响模块数, 需同步调整模块, 调整方案, 监听完整性核查结果
```

- `是否需调整` ∈ {是, 否}：车型形态不含「全形态」（即 ZX-C 旗舰形态当前未覆盖该项）= 是
- `影响模块数` = 模块引用关系表中该数据能力的引用模块总数
- `需同步调整模块` = 引用模块去掉所属模块本身，多个用「、」连接；无外部引用时为「无」
- `监听完整性核查结果` ∈ {通过, 缺失，需补注册更新监听}

## 五、工作流程（workflow）

### STEP 1 · 明确小目标，先立口径

先把需求口径写成显式规则：**ZX-C 旗舰形态下展示全部相关指标，其余形态保持原逻辑不变**。口径不确定时先向需求方确认，不带口径动手。

### STEP 2 · 影响面检索（先查后改）

对每个显示项的数据能力，从 `模块引用关系表.csv` 聚合出引用模块清单，重点关注**文字提示之外的调用方**（如语音助手模块对 getBatterySoc 的同步接口调用）——这类调用方最容易在回归时被遗漏。

### STEP 3 · 逐项判定是否需调整

- 车型形态含「全形态」→ 旗舰形态已覆盖，无需调整
- 车型形态为单形态或组合形态（不含 ZX-C 旗舰）或「不展示」→ 需新增 ZX-C 旗舰形态展示分支，其余形态维持原逻辑

### STEP 4 · 生成调整方案

每个需调整项写清两件事：新增什么分支、哪些形态保持不变。**小步迭代**：一次只改一个明确的小目标，验证后再逐条追加约束。

### STEP 5 · 监听完整性核查

逐项核对 `更新监听` 列：缺失监听的显示项即使逻辑改对也不会刷新。所有缺失项必须在交付物中标注「缺失，需补注册更新监听」。

### STEP 6 · 结果核对与自检

显示与预期不符时，按「配置 → 分支 → 监听 → 数据源」顺序逐层追问定位，不跳层。输出前逐项自检，任一不过则不得输出。

## 六、关键规则（不可协商）

1. **先查影响面，再动手。** 未经影响面检索的显示逻辑调整不得直接实施。
2. **其余形态保持原逻辑。** 调整只新增 ZX-C 旗舰形态分支，不得顺带改其他形态的既有行为。
3. **每个结论可溯源。** 影响模块数与需同步调整模块必须能从 `模块引用关系表.csv` 复算得出。
4. **监听缺失必须显性标注。** 不允许在交付物里静默吞掉缺失项。
5. **AI 只出方案与清单，不改代码。** 分支代码的修改与合入由工程师在 IDE 中完成，涉及跨模块联动的同步调整需对方模块负责人确认。
6. **不承诺效率百分比。** 输出中不写「提升 X%」这类无法核验的表述。

## 七、人工边界

| AI 负责 | 人负责（座舱应用开发工程师） |
| --- | --- |
| 影响面检索与引用清单聚合 | 分支代码的实际修改与自测 |
| 逐项调整方案与监听核查结果 | 跨模块同步调整的对接确认 |
| 显示异常的环节定位建议 | 回归测试范围的决定 |

## 附 · 执行细则（本案例主提示词约束并入）

以下细则来自本场景案例的主提示词，与上文「关键规则」同等效力，执行时一并遵守。

### 执行要求

【执行要求】
1. 先立口径再看显示项：需求为「ZX-C 旗舰形态下展示全部相关指标，其余形态保持原逻辑不变」，把它写成显式判定规则，不要边看边定标准。
2. 影响面检索：对每个显示项的数据能力，从模块引用关系表聚合引用模块清单，标出文字提示之外的调用方（如语音助手模块）。
3. 逐项判定是否需调整：车型形态含「全形态」= 否（旗舰形态已覆盖）；车型形态不含全形态（单形态 / 组合形态 / 不展示）= 是。
4. 生成调整方案：需调整项统一为「新增ZX-C旗舰形态展示分支，其余形态维持原逻辑」；无需调整项标「无需调整，旗舰形态已覆盖」。
5. 监听完整性核查：逐项核对更新监听列，缺失项标「缺失，需补注册更新监听」，不允许静默吞掉。

### 硬性约束

【硬性约束】
- 影响模块数与需同步调整模块必须能从模块引用关系表复算得出，不允许凭印象填写。
- 调整只新增 ZX-C 旗舰形态分支，不得建议修改其他形态的既有行为。
- AI 只输出方案与清单，不直接修改代码；跨模块同步调整需模块负责人确认。
- 监听缺失必须显性标注，不允许省略。
- 不写任何效率百分比或效果承诺。

### 生成后自检

【生成后自检，逐条回答】
1. 20 个显示项是否每行都有影响模块数与需同步调整模块，且可从引用表复算？
2. 需调整项是否都只新增旗舰形态分支、不动其他形态逻辑？
3. 监听缺失项是否全部显性标注？（本次应为 5 处）
4. 电池电量百分比（getBatterySoc）的需同步调整模块是否包含语音助手模块？
5. 是否没有出现任何效率百分比承诺？
自检全过再输出 CSV。

### 输出格式

【输出格式】CSV，8 列，列名与顺序固定：
显示项, 数据能力, 车型形态, 是否需调整, 影响模块数, 需同步调整模块, 调整方案, 监听完整性核查结果
- 需同步调整模块 = 引用模块去掉所属模块本身，多个用「、」连接；无外部引用填「无」
- 影响模块数 = 该数据能力在模块引用关系表中的引用模块总数
