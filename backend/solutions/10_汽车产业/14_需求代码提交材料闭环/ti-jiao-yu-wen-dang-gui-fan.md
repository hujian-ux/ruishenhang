# 提交与文档规范 · 需求代码提交材料闭环

> 适用范围：需求代码合入后的配套材料补齐（提交说明、变更文档、汇报单页、材料清单）。
> 核心原则：**研发过程产生的隐性信息同步固化为可追溯的文档产物**，减少「做过但说不清」的情况。

## 一、四件套齐套口径

每个需求落地后应具备四项配套材料，缺一即为未闭环：

1. **提交说明**：按模板生成的代码提交信息
2. **变更文档**：需求变更说明（固定章节结构）
3. **汇报单页**：面向管理层的单页汇报材料
4. **材料清单**：本需求全部产物的索引清单

完成度 = 既有材料项数 ÷ 4 × 100%。四项齐全（100%）才算材料闭环。

## 二、提交信息模板

```
[需求号][首个涉及模块] 变更内容摘要

变更点：逐条列出本次代码变更内容
影响范围：涉及的模块与显示 / 行为变化
验证方式：自测项与联调验证结论
关联需求号：同批次关联的其他需求号（如有）
```

## 三、变更文档固定章节（六章）

1. 背景：需求来源与触发场景
2. 变更内容：功能层面的具体变化
3. 影响模块：涉及的模块清单与各自改动
4. 接口变化：对外接口 / 数据能力的增删改
5. 验证结论：自测与联调的验证结果
6. 回退方案：出问题时的回退路径与开关

## 四、汇报单页规格

1. 一页呈现，结论先行：第一行说清「做了什么、影响什么、验证结论」
2. 必含三要素：变更内容一句话、影响模块数、验证方式与结论
3. 数据可溯源：页内数字必须能在变更文档或提交说明中找到出处

## 五、技术调研结论的网页化输出

涉及技术选型的需求（如引擎升级、协议引入），调研结论应输出为可查看的网页形式，便于内部分发与评审；网页内容包含：选型对比、结论依据、风险与回退。

## 六、通用约束

1. 材料补齐只描述「该有什么、写了什么」，不替需求本身做决策。
2. 提交说明与变更文档的内容必须与代码提交号对应，禁止张冠李戴。
3. 汇报单页的结论必须与验证结论一致，不允许夸大或缩小。
