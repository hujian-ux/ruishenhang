# 多平台编译构建报错消化

## 一、这个 Skill 解决什么

多芯片平台并行开发意味着编译环境各异，构建脚本执行、产物路径、链接符号等问题频繁出现。真实的消耗不在「看不懂报错」，而在：

- 每个平台的工具链、目录结构、链接配置都不同，经验无法直接平移
- 未定义符号类链接错误的来源有三种可能，猜错方向就是半小时起步的弯路
- 搜索引擎给的是通用答案，不知道你们的 OUT_DIR、条件编译宏和链接列表

本 Skill 的核心动作是**把报错原文直接丢进去，换回结构化归因**，并且保留「是否修改」的人工决策权。

## 二、什么时候用（适用时机）

| 触发情形 | 说明 |
| --- | --- |
| 按构建脚本发起编译后收到一串报错 | 主用场景：逐条分类、归因、给处理方向 |
| 产物没出现在预期目录 | 排查执行目录与产物目录不一致一类问题 |
| 链接阶段大量未定义符号 | 按三类来源逐一排查，不猜单因 |
| 不确定要不要让 AI 直接改 | 三级处置规则先划清只诊不改边界 |

**不适用**：编译通过后的运行时崩溃与系统日志分析（转测试与验证场景）；脚本本身的可用性改造（→ MOB-15）。

## 三、输入（inputs）

| # | 输入文件 | 必需 | 关键字段 |
| --- | --- | --- | --- |
| 1 | `编译报错日志样本.csv` | 必需 | 记录编号、芯片平台、错误类型、报错原文摘要、涉及文件 |
| 2 | `排障决策规则.md` | 必需 | 错误分类定义、未定义符号三类来源、三级处置规则（只诊不改边界） |

> 缺 2（排障决策规则）时，本 Skill **必须拒绝输出处置等级与是否需人工确认两列**，只能给归因建议——处置边界是团队共享的工程约定，不能由 AI 即兴决定。

## 四、输出（outputs）

唯一交付物：`报错归因与处理清单.csv`，字段固定为 8 列：

```
记录编号, 芯片平台, 错误类型, 报错摘要, 归因, 处理方向, 处置等级, 是否需人工确认
```

- `错误类型` ∈ {链接错误, 路径错误, 语法错误}
- `处置等级` ∈ {L1 只诊不改, L2 命令待确认, L3 建议可直接采纳}
- `是否需人工确认` ∈ {是, 否（建议可直接采纳）}
- `归因` 必须写明「来源类别 + 验证方法」，**不允许写「重新编译试试」**

## 五、工作流程（workflow）

### STEP 1 · 先分类，再归因

对每条报错按识别特征分类：链接错误（undefined reference）、路径错误（执行目录 / 产物目录 / No such file / cannot find -l / No rule to make target）、语法错误（expected / macro expands / invalid suffix）。禁止跳过分类直接给修改方案。

### STEP 2 · 未定义符号按三类来源排查

1. 实现文件未参与编译（构建清单遗漏 / 声明与实现签名不一致）
2. 条件编译裁剪（平台宏未开启，stub 文件名是典型线索）
3. 外部库未链接（库未加入链接列表 / 库名不匹配，wrapper、lib 前缀是典型线索）

### STEP 3 · 路径问题对目录

重点排查「执行目录与产物目录不一致」：构建脚本工作目录、OUT_DIR 配置、清理脚本调度时段三者对齐后再发起构建。

### STEP 4 · 三级处置，保留人工决策权

| 等级 | 适用 | 边界 |
| --- | --- | --- |
| L1 只诊不改 | 链接错误 | 只出归因链与验证命令（nm / objdump），不改链接脚本、不开宏 |
| L2 命令待确认 | 路径错误 | 给核对清单与修正命令，执行前人工确认——构建环境是团队共享资产 |
| L3 建议可直接采纳 | 语法错误 | 定位到文件行号给最小修改建议，采纳与执行在 IDE 中由工程师完成 |

### STEP 5 · 逐条推进，自检后输出

一次只处理一条报错，处理完再进入下一条。输出前自检：分类是否完整、归因是否含来源类别与验证方法、处置等级是否与规则一致。

## 六、关键规则（不可协商）

1. **报错原文完整保留。** 不截断、不改写，涉及文件与行号必须在交付物中可见。
2. **链接错误必须给全三类来源。** 只给一种可能等于让工程师赌运气。
3. **AI 不自动修改代码、链接脚本与构建环境。** 是否修改、何时修改由工程师决定；涉及跨模块依赖决策的一律交人工。
4. **路径类修正命令执行前必须人工确认。** 构建环境影响所有并行项目。
5. **一次一条，不交叉。** 多条报错混在一起处理会互相污染归因。
6. **不承诺效率百分比。** 输出中不写「提升 X%」这类无法核验的表述。

## 七、人工边界

| AI 负责 | 人负责（系统与平台适配工程师） |
| --- | --- |
| 报错分类、三类来源归因、验证命令建议 | 是否修改代码与链接配置的决定 |
| 路径问题的核对清单与修正命令 | 构建环境与共享脚本的变更执行 |
| 语法错误的最小修改建议 | 跨模块依赖影响的判断与回归 |

## 八、下游衔接

- 构建适配阶段用到的调试脚本可读性问题 → **MOB-15 设备调试脚本可用性优化**
- 需求落地后的提交说明与变更文档 → **MOB-16 需求代码提交材料闭环**
- 上游：显示逻辑调整涉及的模块改动 → **MOB-13 座舱显示逻辑调整与影响面自查**


## 附 · 执行细则（本案例主提示词约束并入）

以下细则来自本场景案例的主提示词，与上文「关键规则」同等效力，执行时一并遵守。

### 执行要求

【执行要求】
1. 先分类再归因：每条报错先确认错误类型，禁止跳过分类直接给修改方案。
2. 链接错误按三类来源逐一排查：实现文件未参与编译 / 条件编译裁剪（stub 文件名线索）/ 外部库未链接（lib、wrapper 文件名线索），归因必须写明来源类别与验证方法（nm / objdump）。
3. 路径错误按关键词归因：执行目录与 No rule to make target 归工作目录不一致；产物目录归产物被清理；No such file 归头文件路径缺失；cannot find -l 归库搜索路径缺失。
4. 语法错误定位到涉及文件与行号，归因后给出最小修改建议。
5. 处置分级严格执行：链接错误全部 L1 只诊不改；路径错误 L2 命令待确认；语法错误 L3 建议可直接采纳。一次只处理一条，处理完再进下一条。

### 硬性约束

【硬性约束】
- 报错原文完整保留在「报错摘要」列，不截断、不改写。
- 链接错误必须给全来源类别，不允许只写一种可能，更不允许写「重新编译试试」。
- AI 不自动修改任何代码、链接脚本与构建环境变量；路径类修正命令执行前必须人工确认。
- 处置等级与是否需人工确认两列必须与排障决策规则一致，不允许即兴发挥。
- 不写任何效率百分比或效果承诺。

### 生成后自检

【生成后自检，逐条回答】
1. 15 条报错是否每条都有分类、归因、处理方向、处置等级？
2. 归因是否都含来源类别与验证方法，无「重新编译试试」类敷衍表述？
3. 链接错误是否全部标注 L1 只诊不改？（本次应为 6 条）
4. 需人工确认的条数是否等于链接错误与路径错误之和？（本次应为 11 条）
5. 是否没有出现任何效率百分比承诺？
自检全过再输出 CSV。

### 输出格式

【输出格式】CSV，8 列，列名与顺序固定：
记录编号, 芯片平台, 错误类型, 报错摘要, 归因, 处理方向, 处置等级, 是否需人工确认
