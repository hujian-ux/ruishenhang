# 监管报送标准升级与批次改造

## 一、这个 Skill 解决什么

监管报送改造的真实困难不是「新标准读不懂」，而是**历史包袱重、改错代价大**：

- 新标准解读分散在个人理解里，同一条款不同人说法不一
- 存量数据分散在多个历史批次中，只能整体沿用或整体推翻，没人说得清哪些能保
- 边界情况（重录补录时外部无匹配数据）在上线后才暴露，返工成本高
- 未完成事项靠记忆或口头交接，换个会话就断档

本 Skill 的核心动作，是**把风险前移到方案讨论环节**：口径澄清先于编码，每个批次的决策带规则编号，讨论过程与结论写进文档。

## 二、什么时候用（适用时机）

| 触发情形 | 说明 |
| --- | --- |
| 新报送标准下发，系统需按新口径改造 | 主用场景：新旧对比 + 批次梳理 + 方案表 |
| 存量批次太多，说不清哪些能保留哪些要重来 | 按统一规则逐批次判定保留/重构/合并 |
| 重录补录时外部无匹配数据等边界情况 | 先澄清边界情形再进入实现 |
| 改造讨论跨多次会话，怕结论丢失 | 待确认与待完成事项写入需求文档留痕接续 |

**不适用**：日常报送数据本身的加工（属 ETL 作业）；财务检查的批处理与耗时统计（→ FIN-09）。

## 三、输入（inputs）

| # | 输入文件 | 必需 | 关键字段 |
| --- | --- | --- | --- |
| 1 | `历史批次清单.csv` | 必需 | 批次号、数据期间、记录数、当前状态、新标准影响项 |
| 2 | `报送标准新旧对照.md` | 必需 | 9 条新标准条款（新旧口径、差异类型）、决策规则 R1-R5、边界情况口径、工作量分档 |

> 缺 2（新旧对照）时，本 Skill **必须拒绝给出改造决策**——没有条款依据的决策等于拍脑袋，这正是传统模式的病根。

## 四、输出（outputs)

唯一交付物：`批次改造方案表.csv`，字段固定为 9 列：

```
批次号, 数据期间, 记录数, 当前状态, 新标准影响项, 改造决策, 决策依据, 边界情况, 工作量预估人日
```

- `改造决策` ∈ {保留, 重构, 合并}，由规则 R1-R5 按顺序判定
- `决策依据` 必须含规则编号（R1-R5）与条款号（N1-N9），**不允许写「综合判断」**
- `边界情况` 标注重录补录时外部无匹配数据等需人工确认的情形
- `工作量预估人日` 按分档规则计算，保留 0.5 / 合并 1.5 / 重构按记录数 3-5-7 分档

## 五、工作流程（workflow）

### STEP 1 · 新旧口径对比

把新下发标准逐条对照旧口径，输出条款对照（如 N1 字段重命名 / N4 表结构拆分），标注轻度或重度——**先讲清背景再讨论改造**。

### STEP 2 · 历史批次梳理

盘点存量批次：批次号、数据期间、记录数、当前状态（已报送归档 / 报送中 / 待重报 / 已报送待归档）、命中的新标准影响项。

### STEP 3 · 批次改造决策

按规则顺序判定（先命中先生效）：R5 同期多批次待重报 → 合并；R1 无影响 → 保留；R2 轻度影响 + 已报送归档 → 保留（归档不重开）；R3 轻度影响 + 活跃状态 → 重构；R4 重度影响 → 重构。

### STEP 4 · 边界情况澄清

在动代码之前把边界情形写明：重录补录时外部系统无该期间匹配数据按空值口径填 N/A 并人工确认；补录数据已过期的先人工补齐再重报；合并批次以期间主批次为准。**先明确边界再进入实现。**

### STEP 5 · 确认后再改码

方案表逐批次与团队讨论、确认最终更改方案之后才动代码。任何中途调整回到 STEP 3 重判，不直接改表。

### STEP 6 · 留痕与接续

把待确认与待完成事项连同当日工作记录写入需求文档，便于后续继续——跨会话不断档。

## 六、关键规则（不可协商）

1. **先讨论方案、再落代码。** 方案表确认是改码的前置条件，未经确认的方案不产生任何代码变更。
2. **每个决策必须带规则编号与条款依据。** 「这个批次保留」必须能回答「命中了哪条规则、哪条条款」，不允许「综合判断」。
3. **归档批次不轻开。** 已报送归档的批次只有重度影响才考虑重构，轻度影响保留——重开归档批次的风险高于收益。
4. **边界情况先于实现。** 重录补录时外部无匹配数据等情形必须在方案表里写明处理口径，不允许上线后才发现。
5. **工作量用分档规则计算**，不拍脑袋估数；分档规则本身要在对照文档里公开。
6. **不承诺效率百分比。** 本场景输出的是改造范围与工作量事实。

## 七、人工边界

| AI 负责 | 人负责（报送系统研发岗 / 业务条线） |
| --- | --- |
| 新旧口径逐条对比与差异标注 | 新标准条款的最终解释与口径确认 |
| 批次改造决策规则判定与方案表 | 方案表的评审与确认（改码的前置审批） |
| 边界情况梳理与工作量分档计算 | 外部无匹配数据的人工补齐与确认 |
| 待确认事项整理写入需求文档 | 改码实施与上线决定 |

## 八、下游衔接

- 确认后的方案表 → 改码实施与回归验证（工作量 61.5 人日排期）
- 待确认事项清单 → 需求文档留痕，跨会话接续
- 重构批次涉及 13,945 条记录 → ETL 重跑与对账


## 附 · 执行细则（本案例主提示词约束并入）

以下细则来自本场景案例的主提示词，与上文「关键规则」同等效力，执行时一并遵守。

### 执行要求

【执行要求】
1. 新旧口径对比先行：先逐条列出 9 条条款的新旧口径与差异类型，再进入批次判定。
2. 按规则顺序判定每个批次的改造决策（保留/重构/合并），先命中先生效：
   - R5 同一数据期间存在多个待重报批次 → 合并（写明并入哪个主批次）
   - R1 新标准影响项 = 无 → 保留
   - R2 轻度影响 且 已报送归档 → 保留（归档批次不重开）
   - R3 轻度影响 且 活跃状态 → 重构
   - R4 重度影响 → 重构
3. 每行决策依据必须含规则编号与条款号（如「N4 表结构拆分 重度影响（R4）」），不允许写「综合判断」。
4. 边界情况逐行写明：重录补录时外部系统无该期间匹配数据的，按 N9 口径填 N/A 并标注需人工确认；补录数据已过期的先人工补齐再重报；合并批次写明以哪个主批次为准。
5. 工作量预估按分档规则计算（人日），并在表外汇总：总工作量、保留/重构/合并各多少、重构占比。
6. 把「待确认事项」单独列出（含确认后才改码的门禁声明），供写入需求文档留痕接续。

### 硬性约束

【硬性约束】
- 只出方案表，不产生任何代码变更；确认流程必须前置。
- 决策依据不允许写「综合判断」，必须含规则编号与条款依据。
- 影响项与决策的对应必须可复算：任何人按对照文档的规则重跑，应得到完全相同的 25 行决策。
- 不允许出现效率百分比或工期承诺；工作量只按分档规则计算。

### 生成后自检

【生成后自检，逐条回答】
1. 25 个批次的决策分布是否 = 保留 14 / 重构 8 / 合并 3？
2. 每行决策依据是否都含规则编号（R1-R5）？
3. 重构批次工作量是否按记录数分档（3/5/7）？
4. 边界情况是否覆盖重录补录时外部无匹配数据的处理口径？
5. 是否明确「确认之后才改代码」，未夹带任何代码变更？
自检全过再输出 CSV。

批次号, 数据期间, 记录数, 当前状态, 新标准影响项, 改造决策, 决策依据, 边界情况, 工作量预估人日
