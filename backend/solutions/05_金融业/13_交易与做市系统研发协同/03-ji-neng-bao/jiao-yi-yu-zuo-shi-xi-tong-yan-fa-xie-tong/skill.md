# 交易与做市系统研发协同

## 一、这个 Skill 解决什么

做市与交易系统研发的真实困难不是「不会写代码」，而是**接口多、会话状态多，改动牵一发动全身**：

- 接口文档与实现长期不同步，读懂他人代码主要靠口头交接
- 缓存服务传值链路里堆满中间类型转换与冗余类型定义
- 调用脚本按单条手工改写，样式难以保持一致
- 债券损益实体需要按清盘顺序等指标排序汇总，口径每次重新解释
- 接口参数（尤其会话参数）一变，测试用例就要重新编写

本 Skill 的核心动作，是把「理解 — 方案 — 实现 — 文档 — 用例」固定成一条闭环流水线：接口文档是唯一事实源，实现与文档同步演进，用例随参数变化批量再生成。

## 二、什么时候用（适用时机）

| 触发情形 | 说明 |
| --- | --- |
| 参照接口文档实现/改造交易、做市能力 | 主用场景：实现 + 文档同步补全 |
| 缓存服务传值方式重设计 | 减少中间类型转换与冗余类型定义 |
| 需要按既有脚本样式批量构造调用脚本 | 保持团队脚本样式一致 |
| 接口参数变化后测试用例需要批量再生成 | 用例生成加入会话参数并输出会话配置 |

**不适用**：涉及生产环境发布的变更审批（走发布流程）；与接口契约无关的纯算法优化。

## 三、输入（inputs）

| # | 输入文件 | 必需 | 关键字段 |
| --- | --- | --- | --- |
| 1 | `接口文档.md` | 必需 | 接口编号、接口名称、功能说明、输入参数、返回值、会话参数要求、文档状态 |
| 2 | `用例参数矩阵.csv` | 必需 | 序号、接口名称、场景类型、会话参数组合、输入要点、预期行为要点 |

> 缺 1（接口文档）时，本 Skill **必须拒绝生成用例**——没有契约的用例只是臆测。这是本 Skill 最重要的一条硬规则。

## 四、输出（outputs）

唯一交付物：`用例生成与会话配置清单.csv`，字段固定为 8 列：

```
用例编号, 接口编号, 接口名称, 场景类型, 会话参数, 预期输入, 预期返回, 文档同步状态
```

- `用例编号` 形如 `TC-FIN13-001`
- `场景类型` ∈ {正常, 边界, 异常}
- `文档同步状态` ∈ {本次同步补全（接口说明已随实现更新）, 文档已对齐}

## 五、工作流程（workflow）

### STEP 1 · 代码理解与方案比对

在代码上下文里问清实现逻辑（谁在调用、传值链路、会话状态流转）；涉及代码与文档改动时，先给出方案选项，确认后再执行。

### STEP 2 · 按接口文档实现并同步补全文档

参照 `接口文档.md` 实现能力；「待补全」状态的接口段落（参数、返回值、会话参数要求、错误码）在实现合入时同步补全——改完代码顺带把文档补上，接口文档不再是滞后产物。

### STEP 3 · 缓存传值重设计

重新设计缓存服务中的传值方式：结构化载荷直传，减少中间类型转换与冗余类型定义；改动以新增文件为主，对原文有保护要求时不动原始实现。

### STEP 4 · 脚本与用例批量构造

按既有脚本样式批量构造可直接执行的调用脚本；用例生成加入会话参数并输出会话配置内容，接口参数变化后批量再生成。

### STEP 5 · 损益排序汇总

按清盘顺序（clearSeq）等指标对债券损益实体做排序与汇总，口径写进接口文档，不靠口头约定。

### STEP 6 · 自检

输出前逐项自检，任一不过则不得输出：

1. 每条用例的接口是否都能在接口文档中找到定义？
2. 会话参数是否与接口的会话参数要求一致（必填/可选/无）？
3. 「待补全」接口的用例是否都标注了文档同步状态？
4. 正常/边界/异常三类场景是否都有覆盖？

## 六、关键规则（不可协商）

1. **接口文档是唯一事实源。** 矩阵中出现文档未定义的接口必须报错停止，不允许「按猜测生成用例」。
2. **实现与文档同步演进。** 实现合入时必须同步补全文档段落；文档滞后即视为变更未完成。
3. **先要方案、后动代码。** 涉及代码改动先给方案选项，确认后执行；改动以新增文件为主。
4. **用例随参数批量再生成。** 不逐条手工补丁；会话参数变化后整批重算。
5. **不写任何效率百分比或效果承诺。**

## 七、人工边界

| AI 负责 | 人负责（交易系统研发岗） |
| --- | --- |
| 接口定义解析与用例批量生成 | 方案取舍与代码评审 |
| 文档段落补全草稿 | 实现合入与发布审批 |
| 脚本样式对齐与批量构造 | 生产环境变更决定 |
| 会话配置清单整理 | 测试通过标准的最终认定 |


## 附 · 执行细则（本案例主提示词约束并入）

以下细则来自本场景案例的主提示词，与上文「关键规则」同等效力，执行时一并遵守。

### 执行要求

【执行要求】
1. 先读契约再生成：把接口文档总览表解析为显式接口注册表，矩阵中出现文档未定义的接口必须报错停止。
2. 逐条生成用例：按矩阵 20 行顺序编号 TC-FIN13-001 至 TC-FIN13-020；预期输入 = 输入要点 + 会话参数组合；预期返回 = 预期行为要点 + 接口文档声明的返回字段。
3. 会话参数对齐：每条用例的会话参数必须与接口的会话参数要求一致（必填必带、可选标注、无会话参数的接口不得臆造）。
4. 文档同步标注：文档状态为「待补全」的接口，其全部用例标注「本次同步补全（接口说明已随实现更新）」；「完整」接口标注「文档已对齐」。
5. 按既有脚本样式输出：用例编号、预期输入、预期返回的写法与团队既有调用脚本样式保持一致，可直接转成可执行脚本。

### 硬性约束

【硬性约束】
- 每条用例必须能指到接口文档中的具体接口与字段，不允许出现文档之外的接口或参数。
- 会话参数缺失的接口不得臆造会话参数；必填会话参数的接口不得遗漏。
- 文档同步状态只允许两种取值：本次同步补全（接口说明已随实现更新）/ 文档已对齐。
- 用例内容不包含任何生产环境地址、真实账号或令牌。
- 不写任何效率百分比或效果承诺。

### 生成后自检

【生成后自检，逐条回答】
1. 20 条用例是否全部对应接口文档中已定义的 9 个接口之一？
2. 会话参数是否与各接口的会话参数要求逐条一致？
3. 待补全接口（4 个）的用例是否都标注了本次同步补全？
4. 正常 / 边界 / 异常三类场景是否都有覆盖？
自检全过再输出 CSV。

### 输出格式

【输出格式】CSV，8 列，列名与顺序固定：
用例编号, 接口编号, 接口名称, 场景类型, 会话参数, 预期输入, 预期返回, 文档同步状态
