# 互动题型与学习应用功能迭代

## 一、这个 Skill 解决什么

互动题型产品的迭代卡在两件事上：

- **需求散**：拖拽排序、连线匹配、情景选择、发音跟读的细节问题来自四个渠道（教师反馈/用户反馈/产品评审/数据埋点），格式不一、优先级各说各话，排期靠「谁喊得响」；
- **改动乱**：动画时序、音频触发、判定逻辑的调整分散在多个交互组件里，改动边界容易扩大，同类题型要逐个手工排查，返工沟通成本高。

本 Skill 的核心动作：**固定评分公式让优先级可复算 + 版本节奏规则让排期可预期 + 验收要点让回归有依据**，每项需求从进来到进版本走同一条链路。

## 二、什么时候用（适用时机）

| 触发情形 | 说明 |
| --- | --- |
| 双周迭代规划会前，一批待评估需求要排期 | 主用场景：评分 + 版本分配 + 验收要点 |
| 教师渠道集中反馈某题型体验问题 | 按模块聚类查看，判断是否同类回归 |
| 立项争议：这个需求为什么排下个版本 | 评分三列可复算，逐项给出依据 |
| 季度末重评暂缓需求 | 按最新影响用户数重算评分 |

**不适用**：全新题型模块的立项论证（需要单独的产品方案）；线上事故应急响应（走紧急发布流程）。

## 三、输入（inputs）

| # | 输入文件 | 必需 | 关键字段 |
| --- | --- | --- | --- |
| 1 | `功能需求与反馈清单.csv` | 必需 | 编号、类型、标题、涉及模块、提出渠道、影响用户数、当前状态 |
| 2 | `迭代管理规则.md` | 必需 | 优先级评分公式与分档、版本节奏规则、范围与回归规则、输出口径 |

> 缺 2（迭代管理规则）时，本 Skill **必须拒绝输出优先级与版本分配**——评分权重与版本分档必须来自规则文件，不允许临场发明排序标准。

## 四、输出（outputs）

唯一交付物：`需求迭代优先级表.csv`，字段固定为 12 列：

```
编号, 标题, 类型, 涉及模块, 提出渠道, 影响用户数, 影响分, 类型分, 模块分, 优先级评分, 目标版本, 验收要点
```

- `优先级评分` = 影响分×0.5 + 类型分×0.3 + 模块分×0.2，保留 2 位小数
- `目标版本` ∈ {v2.4, v2.5, v2.6, 暂缓}
- `验收要点` 必须可回归（可复测的现象级描述），不允许写「功能正常」这类不可验收的话
- 「X 项进入下一版本」= 目标版本为 v2.4 的行数

## 五、工作流程（workflow）

### STEP 1 · 读规则，先立公式再评分

从 `迭代管理规则.md` 读入评分公式、分档规则与版本节奏，写成显式判定表。先看需求再定权重，等于给结论找理由。

### STEP 2 · 三维打分

对每项需求逐维打分并保留计算列：影响分（按影响用户数分档）、类型分（缺陷 5 / 功能 4 / 反馈 3）、模块分（核心题型模块 5/4，支撑模块 3）。三个分值列必须出现在交付物中，供任何人复算。

### STEP 3 · 评分与版本分配

按公式算优先级评分（保留 2 位小数），再按版本节奏分配：≥3.5 → v2.4；2.5–3.5 → v2.5；<2.5 的缺陷 → v2.6（缺陷不暂缓）；<2.5 的其他 → 暂缓（季度末重评）。

### STEP 4 · 验收要点绑定

每项进入版本的需求按「模块 × 类型」绑定可回归的验收要点，覆盖动画时序、音频触发、判定逻辑与同类题型回归；暂缓项写明重评条件。

### STEP 5 · 自检与人工边界声明

输出前逐项自检，任一不过则不得输出：

1. 交付物行数 = 需求清单行数（逐项对应）？
2. 每行评分是否 = 影响分×0.5 + 类型分×0.3 + 模块分×0.2（保留 2 位小数）？
3. 版本分配是否符合分档规则（含缺陷特例）？
4. 每个排期项是否都有可回归的验收要点？
5. 是否没有任何「谁喊得响谁优先」式的无依据排序？

## 六、关键规则（不可协商）

1. **评分可复算。** 三个分值列保留在交付物中，任何人按公式能算出同样的分；不允许出现无法溯源的「综合优先级」。
2. **缺陷不暂缓。** 体验受损的问题评分再低也进版本排期（v2.6），这是面向低龄学习者的产品底线。
3. **改动范围显式约定。** 每项需求的改动只作用于指定模块，避免影响其他交互组件；同类题型必须回归。
4. **验收必须可回归。** 「功能正常」不是验收要点；要写成「音节高亮与音频触发时机对齐」这类可复测的现象级描述。
5. **暂缓不是拒绝。** 暂缓项写明重评条件（季度末按最新影响用户数重算），不允许静默丢弃。
6. **不承诺效率百分比。** 输出中不写「提升 X%」这类无法核验的表述。

## 七、人工边界

| AI 负责 | 人负责（产品负责人 / 研发负责人） |
| --- | --- |
| 多渠道需求归并与结构化 | 新题型模块的立项论证 |
| 三维打分与版本分配计算 | 版本容量超限时的取舍裁决 |
| 验收要点绑定 | 技术方案与工作量评估 |
| 暂缓项重评条件整理 | 紧急插件的发布决定 |


## 附 · 执行细则（本案例主提示词约束并入）

以下细则来自本场景案例的主提示词，与上文「关键规则」同等效力，执行时一并遵守。

### 执行要求

【执行要求】
1. 先读规则再评分：把评分公式与版本分档写成显式判定表，不要先看需求再定权重。
2. 对 20 项需求逐项打三维分（影响分/类型分/模块分），三个分值列必须保留在输出中供复算。
3. 按公式计算优先级评分（保留 2 位小数），再按版本节奏分配目标版本；注意缺陷特例——评分 <2.5 的缺陷进 v2.6 而非暂缓。
4. 每个排期项按「模块 × 类型」绑定可回归的验收要点，覆盖动画时序、音频触发、判定逻辑与同类题型回归；暂缓项写明季度末按最新影响用户数重评。
5. 改动范围只作用于指定题型组件，验收要点中体现同类题型回归要求。

### 硬性约束

【硬性约束】
- 评分必须可复算：三个分值列保留，不允许出现无法溯源的「综合优先级」。
- 缺陷不暂缓：体验受损的问题评分再低也必须排入版本（v2.6）。
- 验收要点必须可回归（可复测的现象级描述），不允许写「功能正常」。
- 暂缓项必须写明重评条件，不允许静默丢弃。
- 不写任何效率百分比或效果承诺。

### 生成后自检

【生成后自检，逐条回答】
1. 交付物是否 20 行，与需求清单逐项对应？
2. 每行优先级评分是否 = 影响分×0.5 + 类型分×0.3 + 模块分×0.2（逐行抽算）？
3. 进入下一版本 v2.4 的是否恰好 7 项？
4. 版本分布是否 = v2.4 7 项 / v2.5 8 项 / v2.6 1 项 / 暂缓 4 项？
5. 6 项缺陷是否全部排期（v2.4 3 + v2.5 2 + v2.6 1），无一项暂缓？
自检全过再输出 CSV。

【输出格式】CSV，12 列，列名与顺序固定：
编号, 标题, 类型, 涉及模块, 提出渠道, 影响用户数, 影响分, 类型分, 模块分, 优先级评分, 目标版本, 验收要点
