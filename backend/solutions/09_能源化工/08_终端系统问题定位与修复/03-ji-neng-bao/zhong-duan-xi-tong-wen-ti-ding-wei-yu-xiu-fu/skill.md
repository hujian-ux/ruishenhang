# 终端系统问题定位与修复

## 一、这个 Skill 解决什么

终端系统问题的真实困难不是「没日志」，而是**读日志的人跟不上日志产生的速度**：

- 数万字的崩溃堆栈、运行异常与设备日志，人工逐段筛查半天起步
- 依赖冲突、驱动兼容这类问题靠经验与搜索引擎拼凑，口径因人而异
- 问题单只记现象不记归因，同类问题反复发生却对不上根因
- 修复完缺少系统性的验证与回归安排，问题闭环与否说不清

本 Skill 的核心动作：**AI 读日志做归因，人验结论定改法——把问题定位的起点从「人读日志」前移到「AI 读日志」**。

## 二、什么时候用（适用时机）

| 触发情形 | 说明 |
| --- | --- |
| 问题单挂成段日志，需要快速归因 | 主用场景：日志摘要 → 六类根因 |
| 同类问题反复发生，需要统一归因口径 | 六类根因 + 关键词优先级，归因可复核 |
| 修复方案需要按根因模板快速成稿 | 定位路径与修复方案与根因一一对应 |
| 修复后需要判定闭环与回归安排 | 验证结论按严重级别 × 复测轮次判定 |

**不适用**：六类关键词均未命中的日志（→ 标注「待人工归因」，不得强行归类）；构建失败与编译错误（→ 开发排障场景）。

## 三、输入（inputs）

| # | 输入文件 | 必需 | 关键字段 |
| --- | --- | --- | --- |
| 1 | `终端问题记录.csv` | 必需 | 问题编号、机型、问题现象、现象类别、发生条件、日志摘要、严重级别、复测轮次 |
| 2 | `定位方法框架.md` | 必需 | 六类根因关键词与优先级、定位路径模板、修复方案模板、验证结论口径、回归标记口径 |

> 缺 1 中的「日志摘要」列时，本 Skill **必须拒绝归因**——没有日志原文的归因只能是猜测。

## 四、输出（outputs）

唯一交付物：`问题定位与修复表.csv`，字段固定为 11 列：

```
问题编号, 机型, 问题现象, 现象类别, 根因分类, 定位路径, 修复方案,
影响面评估, 验证结论, 回归标记, 严重级别
```

- `根因分类` ∈ {内存资源类, 线程阻塞类, 驱动兼容类, 网络协议类, 配置错误类, 电源管理类, 待人工归因}
- `验证结论` ∈ {复测通过, 复测中（P0 需双轮）, 待复测}
- `回归标记` ∈ {已入回归, 待入回归, 待闭环后入回归}

## 五、工作流程（workflow）

### STEP 1 · 读框架，先立归因口径

从 `定位方法框架.md` 读入六类根因关键词与优先级顺序，写成显式判定表。**先专项后兜底，命中即停**。

### STEP 2 · 日志归因

对每条问题按优先级扫描日志摘要：内存（lowmemorykiller/OOM）→ 线程（blocked/ANR/watchdog）→ 驱动（EDID/HDCP/握手/链路重训练/时序抖动）→ 网络（DHCP/DNS/ARP）→ 配置（配置加载失败/默认配置/参数缺失）→ 电源（suspend/resume/唤醒源）。六类均未命中 → 「待人工归因」。

### STEP 3 · 定位路径与修复方案

按根因分类套用一一对应的定位路径与修复方案模板，逐条成稿。

### STEP 4 · 验证结论判定

按严重级别 × 复测轮次：P0 需双轮、P1 单轮、P2 抽样单轮；轮次不足判「待复测 / 复测中」，达到判「复测通过」。

### STEP 5 · 回归标记与闭环

复测通过的 P0/P1 → 已入回归；P2 → 待入回归；未闭环 → 待闭环后入回归。未闭环问题进入下一轮验证循环。

### STEP 6 · 自检与人工边界声明

输出前逐项自检，任一不过则不得输出（见附录「生成后自检」）。

## 六、关键规则（不可协商）

1. **归因必须指回日志。** 每条根因分类都要能指到日志摘要里的具体关键词，不允许「看起来像」。
2. **六类不命中不强归类。** 兜底标注「待人工归因」，宁可慢不可错。
3. **验证结论可复算。** 严重级别与复测轮次决定结论，P0 双轮闭环是硬规则。
4. **修复方案给路径不给拍板。** 方案成稿供评审，合入与发布决定属于终端软件团队。
5. **不承诺效率百分比。** 输出中不写「提效 X%」这类无法核验的表述。

## 七、人工边界

| AI 负责 | 人负责（终端软件岗） |
| --- | --- |
| 日志摘要归因与关键词命中 | 根因的最终裁决（尤其待人工归因项） |
| 定位路径与修复方案模板成稿 | 修复方案评审与代码合入 |
| 验证结论与回归标记判定 | 发布与否与全量推送决定 |
| 问题台账维护 | 严重级别的定级与调整 |

## 附 · 执行细则（本案例主提示词约束并入）

以下细则来自本场景案例的主提示词，与上文「关键规则」同等效力，执行时一并遵守。

### 执行要求

1. 先读框架再读问题单：把六类关键词优先级、验证结论口径、回归标记口径写成显式判定表。
2. 逐条归因：按 内存→线程→驱动→网络→配置→电源 顺序扫描日志摘要，命中即停；均未命中标注「待人工归因」。
3. 定位路径与修复方案按根因查表套用模板，逐条成稿，不允许自造路径。
4. 影响面按严重级别判定：P0 全量阻断 / P1 高频可复现 / P2 特定条件偶发。
5. 验证结论按严重级别 × 复测轮次：轮次 0 → 待复测；0 < 轮次 < 所需 → 复测中（P0 需双轮）；达到 → 复测通过。

### 硬性约束

- 归因只允许七种取值（六类 + 待人工归因），必须指回日志关键词。
- 验证结论只允许三种取值，必须与严重级别、复测轮次的复算结果一致。
- 回归标记只允许三种取值：复测通过且 P0/P1 → 已入回归；复测通过且 P2 → 待入回归；未闭环 → 待闭环后入回归。
- 不修改原始问题记录；严重级别定级属于终端软件团队。
- 不写任何效率百分比或效果承诺。

### 生成后自检

【生成后自检，逐条回答】
1. 表 20 行是否与问题记录一一对应？
2. 每行根因分类是否指回日志摘要关键词、且按优先级命中即停？
3. 验证结论分布是否可复算？（本案例应为：复测通过 15 / 待复测 4 / 复测中 1）
4. 回归标记分布是否与验证结论一致？（已入回归 8 / 待入回归 7 / 待闭环后入回归 5）
5. 是否没有任何一行被强行归到六类之外或未留证据？
自检全过再输出 CSV。

### 输出格式

CSV，11 列，列名与顺序固定：
问题编号, 机型, 问题现象, 现象类别, 根因分类, 定位路径, 修复方案, 影响面评估, 验证结论, 回归标记, 严重级别
