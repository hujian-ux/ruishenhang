# 嵌入式控制软件开发与现场问题定位

## 一、这个 Skill 解决什么

嵌入式控制软件的真实困难是**开发与排障搅在同一批次里**：

- 一边是新平台的模块开发需求（风扇调速、上电时序、引脚迁移），一边是现场报来的问题（转速抖动、偶发上电失败、停转未告警）
- 现场日志动辄上万行，人工翻日志找规律耗时；验证一个控制假设要手工插日志、重新编译烧录，一轮试错半天起步
- 引脚配置散落多处，改一处漏一处；存疑改动靠人为记忆回退，谁也说不清改了什么

本 Skill 的核心动作，是把两类条目放进**同一张表**统一落档：需求侧逐任务过确认门，问题侧按三条定位路径归因，每个结论都带验证方式与状态。

## 二、什么时候用（适用时机）

| 触发情形 | 说明 |
| --- | --- |
| 一个批次里同时压着模块开发需求与现场问题 | 主用场景：统一落表，避免两边各记一本账 |
| 现场报来运行日志，需要判断某路控制是否真正生效 | 整段日志交 AI 建因果链，人确认硬件事实 |
| 想验证一个控制假设但不想手工插日志重编译 | 走补日志验证路径，AI 生成插桩代码并说明预期输出 |
| 引脚/外设配置改完存疑，不确定改对了没有 | 走配置回退路径，整批回退并标注待确认 |

**不适用**：纯硬件故障的返修判定（属现场工程师职责）；已定版的发布管理流程。

## 三、输入（inputs）

| # | 输入文件 | 必需 | 关键字段 |
| --- | --- | --- | --- |
| 1 | `嵌入式模块与现场问题清单.csv` | 必需 | 条目编号（REQ-/ISS-）、类型（开发需求/现场问题）、所属模块、描述、优先级或严重级 |
| 2 | `开发与定位规范.md` | 必需 | 确认门流程、三类日志埋点、三条定位路径、状态口径、人工边界 |

> 缺 2（规范文件）时，本 Skill 必须拒绝输出——没有先立的规矩，定位路径与状态判定无从执行。

## 四、输出（outputs）

唯一交付物：`模块开发与问题定位表.csv`，字段固定为 8 列：

```
条目编号, 类型, 所属模块, 描述, 优先级或严重级, 实现要点或根因, 验证方式, 状态
```

- 需求行：`实现要点或根因` 写实现要点；`验证方式` = 单元测试 + 代码走查（硬件抽象层迁移类 = 新旧平台接口回归验证）；`状态` = 已完成（经确认门放行）
- 问题行：`实现要点或根因` 写根因分析；`验证方式` = 「定位路径｜明细」，路径 ∈ {日志归因, 补日志验证, 配置回退}；`状态` ∈ {已闭环, 已定位待修复, 已回退待确认}
- 状态由路径＋规则推导：配置回退 → 已回退待确认；补日志验证 → 已闭环；日志归因 → 已闭环或已定位待修复

## 五、工作流程（workflow）

### STEP 1 · 读规范，先立规矩再干活

从 `开发与定位规范.md` 读入确认门流程、埋点规范、三条定位路径与状态口径，写成显式判定表。顺序不可颠倒——先看条目再定口径，等于给结论找理由。

### STEP 2 · 需求逐任务推进

开发需求按「计划—实现—验证—授权」循环拆解：先定实现计划与边界，拆成子任务逐个执行；每个子任务完成后回传实现与验证结果，经人明确确认（往往需要二次、三次确认）才授权进入下一任务或提交。

### STEP 3 · 日志归因建链

整段现场运行日志与状态回显交 AI 建因果链；硬件侧判断（哪一路辅源、哪个反馈引脚）由人给出，AI 负责在代码与日志之间建立对应。

### STEP 4 · 补日志验证

日志不足以下结论时，在关键路径插入日志输出：AI 生成插桩代码并说明预期输出，用实际打印验证控制假设，验证后回收插桩。

### STEP 5 · 回退与标注

存疑的引脚与外设配置先行整批回退并标注「待确认」，由现场工程师确认连接关系后再重新提交；回退类改动不与其他变更混在同一批次。

### STEP 6 · 自检与人工边界声明

输出前逐项自检，任一不过则不得输出（见附录「生成后自检」）。

## 六、关键规则（不可协商）

1. **AI 不做硬件事实判断。** 引脚连接关系、辅路归属、传感器好坏由现场工程师给出；AI 只在代码与日志之间建立对应。
2. **AI 不替人放行。** 每个任务的授权确认与变更的最终决定属于人；确认门往往需要二次、三次确认。
3. **定位路径三选一且必须显式。** 每个问题行的验证方式必须以「日志归因 / 补日志验证 / 配置回退」之一开头，不允许写「综合定位」。
4. **回退必须整批。** 存疑配置先行整批回退并标注待确认，不得只回退部分改动；回退类改动不与其他变更混批。
5. **插桩用完回收。** 补日志验证的插桩代码在假设验证后必须回收，不得残留在发布版本。
6. **不写效率百分比。** 输出中不写「提升 X%」这类无法核验的表述。

## 七、人工边界

| AI 负责 | 人负责（现场工程师） |
| --- | --- |
| 日志因果链建立与可疑点排序 | 硬件事实判断（引脚、辅路、传感器） |
| 插桩验证代码生成与预期输出说明 | 每个任务的授权确认与变更放行 |
| 回退清单整理与待确认项标注 | 待确认项的现场裁决 |
| 实现要点与根因落表 | 修复排期与批次合并决定 |

## 附 · 执行细则（本案例主提示词约束并入）

以下细则来自本场景案例的主提示词，与上文「关键规则」同等效力，执行时一并遵守。

### 执行要求

1. 先读规范再看条目：把确认门流程、三条定位路径与状态口径写成显式判定表，不要先看条目再定口径。
2. 需求行逐条给出实现要点与验证方式（单元测试 + 代码走查；硬件抽象层迁移类为新旧平台接口回归验证），状态记「已完成」的前提是经确认门放行。
3. 问题行逐条给出根因分析，验证方式必须以「日志归因 / 补日志验证 / 配置回退」之一开头并附明细。
4. 状态由路径推导：配置回退 → 已回退待确认；补日志验证 → 已闭环；日志归因 → 已闭环或已定位待修复。
5. 保持输入条目编号（REQ-01~REQ-10 / ISS-01~ISS-08）与原始顺序，逐行对应，不得增删行。

### 硬性约束

- 不允许出现任何真实客户名/品牌名/产品名，案例主体统一以泛称「某算力设备制造企业」叙述。
- 每行「实现要点或根因」必须具体到机制层面（如「回差区间与查表步长重叠」），不允许写「需进一步排查」。
- 不允许出现任何未完成的标记或留空待办的表述。
- 不写任何效率百分比或效果承诺。
- 硬件事实判断与变更放行不得写成 AI 的职责。

### 生成后自检

1. 输出是否 18 行 = 10 条开发需求 + 8 条现场问题，编号与顺序和输入一致？
2. 每个问题行的验证方式是否以三条定位路径之一开头？
3. 状态分布是否为：已完成 10 / 已闭环 4 / 已定位待修复 3 / 已回退待确认 1？
4. 需求优先级分布是否为 高 4 / 中 5 / 低 1；问题严重级分布是否为 致命 1 / 严重 3 / 一般 4？
5. 全表是否无真实企业名、无未完成标记、无效率百分比？
自检全过再输出 CSV。

### 输出格式

CSV，8 列，列名与顺序固定：
条目编号, 类型, 所属模块, 描述, 优先级或严重级, 实现要点或根因, 验证方式, 状态
