# 多形态资料结构化转换与整合

## 一、这个 Skill 解决什么

知识底座的瓶颈不在「没有资料」，而在**资料形态各异、入口不通**：

- 图片里的表格要手工转录，扫描件转出的是不可编辑的文本
- 格式转换易错位，字段缺失靠人工补齐
- 同一件事在多份材料里各说各话，合并口径无从下手
- 不先解决「能不能用」，后续分析与决策都无从开展

本 Skill 的核心动作，是把形态识别、结构转换、去重与冲突处理放进同一张整合清单：每份资料转成多少条、去重多少条、有没有冲突，一行看全、条条可溯源。

## 二、什么时候用（适用时机）

| 触发情形 | 说明 |
| --- | --- |
| 各条线沉淀了一批形态各异的资料需要入库 | 主用场景：形态识别 → 结构转换 → 整合 |
| 图片/扫描件内容需要变成可编辑表格 | OCR 识别与结构化直出 |
| 多份材料按同一主题合并、口径需对齐 | 去重合并 + 冲突标记 |
| 需要一个可检索、可溯源的知识底座 | 每条知识条目指回来源资料编号 |

**不适用**：学术幻灯片套装的结构搭建（→ MED-11）；双语术语统一与正式文书加工（→ MED-12）。

## 三、输入（inputs）

| # | 输入文件 | 必需 | 关键字段 |
| --- | --- | --- | --- |
| 1 | `多形态资料清单.csv` | 必需 | 资料编号、资料名称、形态、来源、关键内容摘要、涉及主题、原始条目数、其中重复条目数 |
| 2 | `知识条目Schema.md` | 必需 | 条目字段定义、主题枚举、转换动作映射、去重规则、冲突处理规则 |

> 缺 2（Schema）时，本 Skill **必须拒绝整合入库**，只可做形态识别与转换。没有统一 schema 的整合，只是把一堆文件挪了个位置。

## 四、输出（outputs）

唯一交付物：`结构化转换与整合清单.csv`，字段固定为 11 列：

```
资料编号, 资料名称, 形态, 涉及主题, 转换动作, 原始条目数, 去重条目数, 入库条目数, 去重标记, 冲突标记, 整合状态
```

- `转换动作` 按形态映射：PDF报告→PDF 解析与条目抽取；会议记录→长文本提炼与结构化；表格→字段校对与格式归一；图片扫描件→OCR 识别与结构化；邮件长文本→要点提炼与主题归类
- `入库条目数 = 原始条目数 − 去重条目数`
- `去重标记` 写明去重条数（同主题合并），无重复则标「无重复」
- `冲突标记` 写明与哪份资料的哪个数据要素不一致；`整合状态` ∈ {已入库, 已入库（冲突待裁决）}
- **冲突双来源条目均保留入库，不得静默丢弃任何一方**

## 五、工作流程（workflow）

### STEP 1 · 形态识别

逐份读 `多形态资料清单.csv`：识别 PDF 报告、会议记录、表格、图片扫描件、邮件长文本五类载体，登记来源与涉及主题。

### STEP 2 · 结构转换

按形态执行对应转换动作：图片转可编辑表格、扫描件 OCR、长文本提炼要点、表格字段校对——输出全部为结构化条目，逐条携带来源资料编号。

### STEP 3 · 按统一 Schema 整合入库

条目归入 11 个主题枚举之一，字段按 Schema 定义落位，形成可检索的知识底座。

### STEP 4 · 去重与冲突标记

同主题要点重复的条目合并（入库条目数 = 原始 − 去重）；同一数据要素在不同来源数值不一致时**双保留**，后入库一方标记「冲突待裁决」，提交知识管理委员会人工裁决。

### STEP 5 · 清单落盘与移交

整合清单落盘；冲突条目移交人工裁决，裁决前不参与下游引用。

## 六、关键规则（不可协商）

1. **原始材料只读。** 转换一律在副本上进行，原始资料保持只读。
2. **条条可溯源。** 每条知识条目必须指回来源资料编号（D01–D20），无来源不入库。
3. **冲突不得静默处理。** 数值不一致的双来源条目均保留并标记，丢弃任何一方都是数据事故。
4. **去重不等于删数据。** 合并保留信息最全的一条，去重条数必须写明且可复算。
5. **冲突裁决属于人。** 知识管理委员会裁决前，冲突条目不参与下游引用。
6. **不承诺效率百分比。** 输出中不写「提升 X%」这类无法核验的表述。

## 七、人工边界

| AI 负责 | 人负责（知识管理岗 / 知识管理委员会） |
| --- | --- |
| 形态识别与结构转换 | Schema 与主题枚举的维护 |
| 去重合并与条数核算 | 冲突数值的人工裁决 |
| 冲突标记与移交清单 | 知识底座的发布与权限管理 |

## 附 · 执行细则（本案例主提示词约束并入）

以下细则来自本场景案例的主提示词，与上文「关键规则」同等效力，执行时一并遵守。

### 执行要求

【执行要求】
1. 先识别形态再转换：逐份登记形态（PDF报告 / 会议记录 / 表格 / 图片扫描件 / 邮件长文本）与涉及主题，不要跳过识别直接抽取。
2. 按映射执行转换动作：PDF报告→PDF 解析与条目抽取；会议记录→长文本提炼与结构化；表格→字段校对与格式归一；图片扫描件→OCR 识别与结构化；邮件长文本→要点提炼与主题归类；每条条目必须指回来源资料编号。
3. 按统一 Schema 整合入库：条目归入 11 个主题枚举之一，原始材料保持只读，转换在副本上进行。
4. 去重与冲突标记：入库条目数 = 原始条目数 − 去重条目数，去重条数写明；数值冲突双保留，标明与哪份资料的哪个数据要素不一致（D06 vs D05 竞品A中位OS / D07 vs D01 中位PFS / D09 vs D14 3级事件计数 / D17 vs D01 ORR / D20 vs D13 累计入组数）。
5. 整合状态出具：无冲突资料标「已入库」，冲突资料标「已入库，冲突待裁决」，裁决前不参与下游引用。

### 硬性约束

【硬性约束】
- 每条知识条目必须可溯源到来源资料编号，无来源不入库。
- 冲突不得静默处理：双来源条目均保留并标记，丢弃任何一方都是数据事故。
- 入库条目数必须等于原始条目数减去重条目数，逐份可复算。
- 原始材料保持只读，转换一律在副本上进行。
- 交付物必须为 20 行，与资料清单逐行对应，不允许增删行；不写效率百分比。

### 生成后自检

【生成后自检，逐条回答】
1. 20 行输出是否与资料清单逐行对应？
2. 入库条目合计是否为 86 条（原始 104 − 去重 18）？
3. 冲突待裁决是否恰好 5 处（D06/D07/D09/D17/D20）？
4. 每份资料的入库条目数是否 = 原始条目数 − 去重条目数？
自检全过再输出 CSV。

【输出格式】CSV，11 列，列名与顺序固定：
资料编号, 资料名称, 形态, 涉及主题, 转换动作, 原始条目数, 去重条目数, 入库条目数, 去重标记, 冲突标记, 整合状态
