# 售后工程师知识体系与服务系统自建

## 一、这个 Skill 解决什么

售后团队的真实困难不是「不会修」，而是**知道怎么修的人不在现场**：

- 厂家维修手册篇幅长、专业度高，新人上手慢，跟师傅学周期以月计
- 现场故障与解决方案散落在个人经验里，人走了经验就走了
- 工单记录只当流水账存档，没人做频次统计，派单凭感觉
- 高频故障没有标准处置口径，不同工程师处理同一现象耗时差一倍

本 Skill 的核心动作，是把工单流水按「现象—原因—处置」三级归档，把「老师傅脑子里的判断」变成可检索、可统计、可派单的知识表——新工程师按现象检索即可独立处置大部分常见故障。

## 二、什么时候用（适用时机）

| 触发情形 | 说明 |
| --- | --- |
| 积累了一批工单记录，想沉淀成知识库 | 主用场景：三级归档 + 频次统计 |
| 新工程师接单前需要处置指引 | 按现象检索最可能原因与标准处置 |
| 派单规则需要数据支撑 | 高频/中频/低频分级 + 平均耗时 |
| 自建服务系统需要知识库底表 | 输出表可直接作为报单/派单/检索模块的数据基础 |

**不适用**：仍在厂家保修期内、必须原厂工程师处置的故障（只做登记与转派）；设备选型与采购评估（→ MED-06 采购与仓储数字化协同开发）。

## 三、输入（inputs）

| # | 输入文件 | 必需 | 关键字段 |
| --- | --- | --- | --- |
| 1 | `维修工单记录.csv` | 必需 | 工单号、设备类型、故障现象、处置动作、维修耗时（小时）、工程师 |
| 2 | `知识体系框架.md` | 必需 | 三级分类规则（L1/L2/L3）、8 类映射表、频次分级与派单规则、覆盖率判定 |

> 缺 2（框架文件）时，本 Skill **必须拒绝输出派单优先级**，只能输出不带分级的频次统计。框架先行是知识体系的前提。

## 四、输出（outputs）

唯一交付物：`故障知识体系与派单规则表.csv`，字段固定为 7 列：

```
故障现象, 出现次数, 工单占比, 最可能原因, 标准处置, 平均耗时（小时）, 派单优先级
```

- 行数 = L1 类目数（按出现次数降序）
- `最可能原因` / `标准处置` = 框架文件 L1 映射表的 L2 / L3
- `平均耗时` = 该类工单维修耗时合计 ÷ 出现次数（保留 1 位小数）
- `派单优先级` ∈ {高频重点, 中频常规, 低频备案}，按出现次数判定
- 输入中每张工单的处置动作必须与映射表 L3 一致，不一致先复核工单再决定是否新增类目

## 五、工作流程（workflow）

### STEP 1 · 读框架，先立类目再看工单

从 `知识体系框架.md` 读入 L1 类目映射表与频次分级规则。**顺序不可颠倒**——先看工单再归类目，容易把现象描述五花八门的同类故障拆成多类。

### STEP 2 · 工单归档与一致性校验

把每张工单归入一个 L1 类目；校验工单的处置动作与 L3 标准处置是否一致，不一致的先复核记录。

### STEP 3 · 频次与耗时统计

逐类统计出现次数、工单占比、平均耗时；计算高频故障覆盖率 = 前 N 类出现次数合计 ÷ 工单总数。

### STEP 4 · 派单分级

- 出现次数 ≥ 6 → 高频重点：优先派资深工程师，纳入预防性维护清单
- 3 ~ 5 → 中频常规：按标准流程派单
- ≤ 2 → 低频备案：接单后先检索知识库处置

### STEP 5 · 落地为服务系统

输出表作为自建服务系统（报单、派单、知识检索）的数据底表：接单时按现象匹配 L1 → 派单按分级匹配工程师 → 处置完回写工单沉淀记录。

### STEP 6 · 自检与人工边界声明

输出前逐项自检，任一不过则不得输出（见主提示词【生成后自检】）。

## 六、关键规则（不可协商）

1. **框架先行。** 没有三级分类框架不得输出派单优先级。
2. **每张工单必须归入一个 L1 类目。** 归不进去的现象是「新增类目」的信号，先复核再入库，不允许硬塞。
3. **一致性校验。** 工单处置动作与 L3 不一致时必须暴露，不允许静默通过。
4. **最可能原因是统计结论。** 来自历史工单的首位原因，不排除其他可能性；处置失败时要回查 L2 是否误判。
5. **AI 不替代现场判断。** 知识表是处置指引不是处置决定；疑难故障、涉及安全件的更换必须资深工程师复核。
6. **不承诺效率百分比。** 输出中不写「提升 X%」这类无法核验的表述。

## 七、人工边界

| AI 负责 | 人负责（售后服务负责人 / 资深工程师） |
| --- | --- |
| 三级归档与频次统计 | 新增类目与 L2 原因的确认 |
| 派单分级与覆盖率计算 | 疑难故障的现场处置 |
| 服务系统底表生成 | 涉及安全件更换的复核签字 |

## 八、下游衔接

- 高频重点类 → 预防性维护清单与备件备货计划（对接 **MED-06 采购与仓储数字化协同开发**）
- 知识表 → 新工程师培训与考核出题
- 工单回写 → 月度复盘：频次变化、平均耗时异常检测


## 附 · 执行细则（本案例主提示词约束并入）

以下细则来自本场景案例的主提示词，与上文「关键规则」同等效力，执行时一并遵守。

### 执行要求

【执行要求】
1. 先读框架再看工单：先固化 L1 类目与分级规则，再开始归档，不要看完工单再反推类目。
2. 逐单归档：把 30 张工单逐张归入 L1 类目；归不进去的现象先标注「待新增类目」，不允许硬塞。
3. 一致性校验：每张工单的处置动作必须与映射表 L3 标准处置比对，不一致的工单号要单独列出。
4. 频次与耗时统计：按类统计出现次数、工单占比、平均耗时（保留 1 位小数），按出现次数降序排列。
5. 覆盖率结论：给出「前 4 类高频故障覆盖多少工单」的结论，并回指具体行。
6. 派单分级：按 ≥6 / 3~5 / ≤2 规则逐类打派单优先级，作为自建服务系统派单模块的规则底表。

### 硬性约束

【硬性约束】
- 最可能原因与标准处置必须取自框架文件的映射表，不允许自行编造新原因。
- 平均耗时保留 1 位小数；工单占比保留 1 位小数。
- 不写任何效率百分比或效果承诺；不出现真实企业与品牌名。
- 输出必须全部为正式结论与实测值，不得含任何非正式表述。

### 生成后自检

【生成后自检，逐条回答】
1. 输出是否为 8 行（30 张工单全部归档，无遗漏无重复）？
2. 出现次数分布是否为 7/6/5/4/3/2/2/1，合计 30？
3. 前 4 类是否覆盖 22 张工单 = 73.3%？
4. 平均耗时列是否与工单明细逐组复算一致（如样本针堵塞 11.2 ÷ 7 = 1.6）？
5. 是否有任何一张工单的处置动作与 L3 不一致？
自检全过再输出 CSV。

### 输出格式

【输出格式】CSV，7 列，列名与顺序固定：
故障现象, 出现次数, 工单占比, 最可能原因, 标准处置, 平均耗时（小时）, 派单优先级
