# 内部系统原型到功能模块生成

## 一、这个 Skill 解决什么

内部系统建设的真实困难不是「写不出代码」，而是**原型与实现之间的一致性**：

- 原型到实现靠口头对齐，做出来不是业务想要的
- 组件划分靠临时决策，多页面风格漂移、结构不一致
- 字段定义阻塞在接口进度上，接口不动、页面全停
- 非技术岗提了需求就插不上话，确认环节形同虚设

本 Skill 的核心动作，是**把「原型 → 组件 → 字段 → 页面」变成连续动作**：需求先定型为原型模块（机械规则判定），确认后按原型直接生成，字段先行定义不阻塞接口。

## 二、什么时候用（适用时机）

| 触发情形 | 说明 |
| --- | --- |
| 业务岗位提出内部工具需求 | 主用场景：需求清单 → 原型模块 → 实现方案表 |
| 原型已确认，需要生成功能模块 | 按原型页面结构逐页生成，风格一致 |
| 接口未就绪但页面要先做 | 字段先行定义挂到组件，接口就绪后调整 |
| 多页面系统需要统一结构 | 逐页推进，按同一规范判定模块类型与生成方式 |

**不适用**：对外客户系统建设（属产研流程）；既有系统的接口联调（属研发排期）。

## 三、输入（inputs）

| # | 输入文件 | 必需 | 关键字段 |
| --- | --- | --- | --- |
| 1 | `内部系统需求清单.csv` | 必需 | 需求编号、需求名、提出岗位、当前做法、期望功能、数据字段、模块类型、归属数据表、原型状态 |
| 2 | `原型设计规范.md` | 必需 | 模块类型划分、命名规范、生成方式判定（字段数 ≥7 组件拆分）、交互约定、字段映射规则、状态口径 |

> 缺 2（设计规范）时，本 Skill **必须拒绝输出**——模块类型与生成方式的判定规则不是临场发挥，是机构信息化建设的正式口径。

## 四、输出（outputs）

唯一交付物：`原型与模块实现方案表.csv`，字段固定为 6 列：

```
需求, 原型模块, 生成方式, 数据字段映射, 衔接流程, 状态
```

- `需求` = 需求编号 + 需求名（与需求清单一致，12 行）
- `原型模块` = 模块类型 + 「 · 」+ 需求名 + 「页」（命名规范第二节）
- `生成方式` ∈ {单页生成, 组件拆分生成（主组件+子组件）}，按字段数判定（第三节）
- `数据字段映射` = 归属数据表 + 字段数 + 字段清单（第五节）
- `衔接流程` 按模块类型取固定口径（第四节）
- `状态` ∈ {模块已生成，字段已定义，接口后对接, 待原型确认，原型草图已出}（第六节）

## 五、工作流程（workflow）

### STEP 1 · 读规范，先立口径

从 `原型设计规范.md` 读入模块类型划分、命名规范、生成方式判定与交互约定，写成显式判定表。**顺序不可颠倒**——先看需求再定规则，等于给结论找理由。

### STEP 2 · 逐项定型

对每项需求按功能形态定模块类型（表单/列表/查询统计），按命名规范生成原型模块名。

### STEP 3 · 判定生成方式

数数据字段数：≥7 组件拆分生成（主组件+子组件），<7 单页生成。组件拆分的模块标注「字段先行，接口后对接」。

### STEP 4 · 字段映射与衔接

字段清单映射到归属数据表（字段数 + 清单），衔接流程按模块类型取固定口径。

### STEP 5 · 状态与推进

原型已确认 → 状态「模块已生成，字段已定义，接口后对接」；待确认 → 「待原型确认，原型草图已出」。实现方案表交给提出岗位在原型页面上核对字段与交互，确认后逐页生成。

### STEP 6 · 自检

输出前逐项自检，任一不过则不得输出：

1. 模块类型分布是否与需求功能形态逐一吻合？
2. 生成方式是否全部按字段数判定（≥7 拆分）？
3. 字段映射的清单与需求清单是否逐字段一致？
4. 状态是否与原型状态逐一对应？

## 六、关键规则（不可协商）

1. **原型先行。** 任何需求先出原型（界面草图 + 交互说明），提出岗位确认后再生成模块，不做「边写边对齐」。
2. **字段先行，接口后接。** 字段定义不阻塞在接口进度上；接口就绪后按接口调整，不回改需求字段名。
3. **判定必须机械可复算。** 模块类型、生成方式、状态全部按规范判定，不允许「综合考虑」。
4. **逐页推进。** 多页面按同一结构推进，组件划分按规范执行，避免风格漂移。
5. **AI 不替代最终验收。** 原型确认、字段核对与上线验收由提出岗位与信息化建设岗人工完成。
6. **不承诺效率百分比。** 输出中不写「提升 X%」这类无法核验的表述。

## 七、人工边界

| AI 负责 | 人负责（信息化建设岗 / 提出岗位） |
| --- | --- |
| 模块类型判定与原型模块命名 | 设计规范（模块划分/交互约定）的制定 |
| 生成方式判定与字段映射 | 原型页面确认与字段核对 |
| 实现方案表初稿 | 生成代码的上线验收 |
| 规则一致性自检 | 接口就绪后的字段调整决策 |

## 八、下游衔接

- 已确认需求 → 按实现方案表逐页生成功能模块，进入开发排期
- 待确认需求 → 原型草图发提出岗位确认，确认后回到本流程 STEP 3
- 查询统计类模块（如时效达标率统计）→ 产出数据供 MED-01 区域经营复盘直接使用


## 附 · 执行细则（本案例主提示词约束并入）

以下细则来自本场景案例的主提示词，与上文「关键规则」同等效力，执行时一并遵守。

### 执行要求

【执行要求】
1. 先读规范再看需求：把模块类型、命名、生成方式、交互约定写成显式判定表，不要先看需求再定标准。
2. 逐项定型：对 12 项需求按功能形态定模块类型，按命名规范生成原型模块名。
3. 判定生成方式：逐项数字段数——≥7 标「组件拆分生成（主组件+子组件）」；<7 标「单页生成」。
4. 字段映射与衔接：每项写「归属数据表（N 字段）：字段清单」，衔接流程按模块类型取固定口径。
5. 状态判定：原型状态=已确认 → 模块已生成；待确认 → 待原型确认。统计整体：模块类型分布、生成方式分布、已生成/待确认数、字段总数。

### 硬性约束

【硬性约束】
- 模块类型、生成方式、状态全部按规范机械判定，不允许「综合考虑」。
- 字段映射必须逐字段照抄需求清单，不得增删改字段名。
- 原型未确认的需求只标注状态，不生成模块实现细节。
- 接口就绪前字段先行定义，输出中不得出现「等待接口再定义字段」的表述。
- 不写任何效率百分比或效果承诺。

### 生成后自检

【生成后自检，逐条回答】
1. 12 项是否全部有原型模块名且符合命名规范？
2. 字段数 ≥7 的项是否全部为组件拆分生成？
3. 字段合计是否等于逐项字段数之和？
4. 模块类型分布是否与需求清单一致？
自检全过再输出 CSV。

### 输出格式

【输出格式】CSV，6 列，列名与顺序固定：
需求, 原型模块, 生成方式, 数据字段映射, 衔接流程, 状态
