# VOC 产品质量闭环 · Skill

## 一、这个 Skill 解决什么

跨境电商的「质量问题」经常是假问题：仓库 Disposition 标 `Defective` 只代表**不可再售**，
里面混着「已开封无法复原」这类非质量情形；而客户退货备注写的是 `too small` / `not as expected`——
两套语言说的是两件事。按 Disposition 追责供应商就是冤案，真正该改的 Listing 图没人改。

本 Skill 把三个系统里的 VOC 拼到一起，用**客户原话**推翻仓库标签，并把结论落成有责任岗位、
有验收标准、有截止日的 CAPA 表。

## 二、什么时候用（适用时机）

- 某 SKU 差评/退货/工单同时上升，但三个部门给出三种解释
- 准备向供应商提质量索赔、或供应商要求撤销索赔时的定责复核
- Listing 改图/改文案后出现异常波动，需要确认「是不是图带偏了」
- 质量月会前需要一份能签字的 CAPA 闭环表
- 同类问题连续 2 个月以上重复出现（组织失忆）

**不适用**：单条差评的应答话术撰写；产品设计方案评审；供应商商务谈判。

## 三、输入（inputs）

| 输入 | 必需 | 格式 | 关键字段 |
| --- | --- | --- | --- |
| 差评明细 | 必需 | CSV | review_id, sku, review_date, marketplace, language, star_rating, review_title, review_body, listing_version |
| 退货报告（FBA / 海外仓） | 必需 | CSV | return_id, order_id, sku, return_date, platform_reason_code, **customer_comment**, **warehouse_disposition**, **warehouse_note**, unit_loss_usd |
| 客服工单 | 必需 | CSV | ticket_id, sku, created_date, channel, subject, customer_verbatim, resolution |
| 产品规格与 Listing 变更档案 | 必需 | MD | 三维尺寸基准、Listing 版本上线日期与变更内容、Disposition 口径、责任岗位对照表 |

> `customer_comment` 与 `warehouse_note` 是本 Skill 的**星标字段**——绝大多数团队不会去看退货表的备注栏。

## 四、输出（outputs）

| 输出 | 格式 | 内容 |
| --- | --- | --- |
| VOC 质量闭环表 | CSV | 主题 / VOC 合并条数 / 占比 / 退货单数 / 单均损失 / 损失金额 / 星标证据编号 / 发生原因 / 流出原因 / 根因判定 / CAPA 编号 / 动作 / 类型 / 责任岗位 / 验收标准 / 目标完成日 / 状态，末行为合计校验行 |
| 结论摘要 | 对话正文 | 聚类占比（必须算平）、误判单数、金额影响、拐点日期、方案一/方案二 |

## 五、工作流程（workflow）

### STEP 1 · 三源数据对齐
1. 统一 SKU 主键与时间窗（默认近 90 天，明确起止日期）。
2. 统一日期字段：差评用 review_date、退货用 return_date、工单用 created_date，全部转 `YYYY-MM-DD`。
3. 统一语言：多语言评论保留原文，仅在主题标签上做统一（不翻译原文，避免证据失真）。
4. 输出对齐后条数：`差评 + 退货 + 工单 = VOC 合并条数`，并在正文报出三项分量。
5. **口径红线**：三源不去重（同一客户可能既留差评又退货），合并条数用于**主题权重**，金额只用退货表算。

### STEP 2 · 问题聚类（占比必须算平）
1. 用客户原话（review_body / customer_comment / customer_verbatim）打主题标签，不用平台原因码打标签。
2. 主题集合建议：`尺寸误解 / 噪音 / 漏水 / 其他`（按 SKU 实际调整，不超过 6 类）。
3. 每条只归一个主类，占比之和必须等于 100.0%，各类条数之和必须等于 VOC 合并条数——**算不平不许往下走**。
4. 「其他」类占比 > 5% 时，必须做二次标注并列为一条 CAPA。

### STEP 3 · 星标素材提取（推翻标签）
1. 交叉核对：`warehouse_disposition = Defective` 且 `customer_comment` 含 `too small` / `not as expected` / `wrong size` 的行，逐条列出 return_id。
2. 核对 `warehouse_note`：若写「通电正常/功能测试通过/无渗漏」，则该单**不构成质量失效证据**。
3. 报出误判单数与占比，并明确：这些单不得计入质量退货、不得向供应商索赔。
4. 找拐点：把主题条数按 Listing 版本上线日切分，计算上线后 14 天日均 vs 其余时段日均，倍数 ≥2 即认定为 Listing 变更相关。

### STEP 4 · 双路径归因
每个主题必须分别回答两件事，缺一不算完成：
- **为什么发生（occurrence）**：产品/信息/包装层面的直接原因，必须引用规格档案里的具体数值。
- **为什么没被拦住（escape）**：流程层面缺了哪个检查点（审校项、检验项、对齐机制）。

再做根因分类，二选一：
- `产品失效` → 保留 Defective 定责，走品质/采购/供应商路径。
- `描述性预期差` → 责任在运营/设计/客服，禁止向供应商追责。

### STEP 5 · CAPA 派工与闭环
1. 每个主题至少 2 条 CAPA，且必须覆盖「改内容」与「补流程」两侧。
2. 每条 CAPA 必填：动作类型（改描述文字 / 改图 / 改话术 / 加质检项 / 供应商整改 / 定责更正 / 归类细化 / 流程闭环）、责任岗位（到岗位名，不写部门）、**可核对的验收标准**、目标完成日、状态。
3. 排序规则：零成本动作（改描述文字）优先且给 48 小时内截止；改图类给 7–14 天。
4. 收尾写入两条硬规则：
   - 尺寸图未上线前，不得判定「已解决」；
   - 上线后 30 天复测，尺寸类退货占比 ≤ 目标值才允许结案。

## 六、关键规则（必须遵守）

1. **Disposition 不等于根因**：仓库标签只回答「能不能再售」，根因必须回到客户原话 + 规格数值。
2. **金额只从退货表算**：`主题损失 = 该主题退货单数 × 该主题单均损失`，四类相加为总损失，禁止用差评条数估算金额。
3. **不承诺效率百分比**：只报可复算的条数、占比、金额、日期。
4. **人工边界**：AI 只做对齐、聚类、归因、CAPA 生成；以下必须人做——
   - 产品根因与质量责任的最终认定
   - Listing 修改的确认与上线
   - 供应商沟通与索赔/撤销索赔决定
5. **证据可回溯**：表中每条星标证据必须写真实的 return_id / review_id / ticket_id，不允许写「若干单」。
6. **不改客户原文**：多语言原话保留，避免翻译造成语义漂移。

## 七、内置提示词骨架

```
你现在按 voc-quality-closed-loop 技能处理 SKU {SKU} 近 {N} 天的 VOC 数据。
素材：差评明细.csv / FBA退货报告.csv / 客服工单.csv / 产品与Listing档案.md

按五步输出：
1) 三源对齐：报出差评/退货/工单条数与合并条数，说明时间窗与不去重口径
2) 问题聚类：4 类主题的条数与占比，占比之和必须 = 100.0%，条数之和必须 = 合并条数
3) 星标素材：列出 warehouse_disposition=Defective 且 customer_comment 含 too small/not as expected 的 return_id，
   报出误判单数与占比，并给出「不得向供应商索赔」的结论；同时给出 Listing 版本拐点的日均倍数
4) 双路径归因：每个主题分别写「为什么发生」与「为什么没被拦住」，并判定 产品失效 / 描述性预期差
5) CAPA 闭环表：CSV，字段见 outputs，末行为合计校验行

自检：占比算平了吗？金额 = 退货单数 × 单均损失 吗？每条 CAPA 有责任岗位和验收标准吗？
尺寸图未上线前是否避免了「已解决」结论？零成本方案是否排在改图前面？
```

## 八、常见失败模式

| 失败模式 | 表现 | 纠正 |
| --- | --- | --- |
| 用平台原因码当主题 | 全部归到 DEFECTIVE，聚类无信息量 | 改用客户原话打标签 |
| 占比算不平 | 61% + 19% + 11% + 9% = 100% 但条数和不等于合并条数 | 先定条数再算占比，四舍五入误差落在最大类 |
| 只写发生原因 | CAPA 全是「改图」，流程漏洞照旧 | 强制补 escape 原因与流程类 CAPA |
| CAPA 无验收 | 状态永远「进行中」 | 每条给可核对的验收物（页面截图/版本号/检测报告） |
| 改完就结案 | 下月同类工单继续来 | 30 天复测 + 占比目标值才允许结案 |
