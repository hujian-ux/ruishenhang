现状与痛点

批量上架的错误，绝大多数不是刊登工具不好用，而是主数据与平台 Schema 对不上。ERP 回执逐条点开排查极其耗时，而且改完再发、错了再改，来回三四轮。

回执报出 42 个字段错误

美国站 HT-K09、HT-L10 共 6 个变体 SKU 批量上架，ERP 首轮回执：2 个图片尺寸不足、1 个类目错选、3 个变体关系挂错，合计 42 个字段错误。

高频
变体关系频繁挂错

旧系统把颜色变体建成独立 SKU，新主数据要求父子体。两套规则并存时，变体关系必错，父子体被拆散。

高风险
错类目带来隐形损失

类目选错不会立刻报错，但搜索流量分配全错。海拓 HT-K02 历史上错类目 7 天损失约 1,900 USD 销售额才发现。

成本浪费
发布无审批与回执闭环

批量发布点下去，谁审的、哪条成功、哪条失败、失败后改了什么没有留痕，第二次发还是同样错。

耗时

批量上架的错误不是技术错误，是主数据错误——根子往往出在一张没人想起的旧映射表上。

WorkBuddy 的解决与价值

WorkBuddy 把"产品资料 → 平台字段 → 校验 → 审批 → 发布 → 错误回执"做成一条可复跑的流水线：主数据先校验，错误按三类归因定位，分批发布全程留痕。

传统做法

运营对着 ERP 回执逐条点开 42 个错误，改完再发、错了再改，来回三四轮；变体关系凭感觉挂，挂错了父子体被拆；没人记录这次改了什么，下次上架重新踩。

WorkBuddy 做法

主数据先校验（必填字段、图片规格、类目、变体），错误按图片/类目/变体三类归因定位，每条给修改对照；发布分批：无争议先发，争议项修正后重试，回执闭环留痕。

三个核心价值
01把散在多处的东西拼到一起

主数据表、平台 Schema、旧 ERP 映射表一次性对齐，变体规则冲突根源一眼可见，不再逐条点开猜错在哪。

02错误分类归因而非堆回执

42 个字段错误归口到图片/类目/变体三类，每条定位到具体 SKU 与字段，并给出"平台要求 vs 当前值 vs 修正动作"对照。

03分批发布 + 全程留痕

无争议先发 3 个、变体争议 3 个留待人工确认后重试；谁审的、哪条成功失败、改了什么都有记录，杜绝重复踩坑。

方案定位

不是替运营点发布，而是把"主数据校验 + 错误归因 + 分批发布闭环"做成可复跑的生产线，高风险动作（变体/类目/正式发布）一律人工审批。

解决方案的工作流程

整体流程五步走，运营只在最后做业务确认，其余由 Skill 驱动自动完成。

脱敏案例：海拓生活科技 · 美国站

6 个变体 SKU（HT-K09、HT-L10 各 3 色）批量上架，ERP 首轮回执 42 个字段错误。星标素材是一张旧 ERP 映射表——颜色变体被建成独立 SKU，与新父子体规则冲突，这正是变体关系挂错的根因。错类目的历史代价同样沉重：HT-K02 曾因错类目 7 天损失约 1,900 USD 销售额。结论：变体映射未确认前不批量发布，方案一先发 3 个无争议 SKU。

提示词
TRAINING PROMPT · 复制即用
请基于以下两份素材，为「海拓生活科技 · 美国站」执行 Amazon 及多平台商品批量上架校验，严格按 5 段输出。

【输入 1 · 商品上架主数据】（节选自 商品上架主数据.csv）
- 每行一个 SKU：HT-K09-Black / HT-K09-White / HT-K09-Blue / HT-L10-Black / HT-L10-White / HT-L10-Red
- 字段含：父SKU、产品系列、颜色、变体主题、提交类目节点、推荐类目节点、主图尺寸、附图数量、证书状态、变体关系状态、归属站点
- 当前 6 个变体 SKU，ERP 首轮回执共报 42 个字段错误

【输入 2 · 旧ERP_SKU映射表】（节选自 旧ERP_SKU映射表.csv · 星标素材）
- 旧系统把颜色变体建成独立 SKU，新主数据要求挂父子体
- HT-K09 / HT-L10 系列均存在该规则冲突，是变体关系挂错的根因
- 历史参考：HT-K02 曾因错类目 7 天损失约 1,900 USD 销售额

【平台 Schema 要求】
- 图片：主图≥1000x1000px、纯白底、商品占比≥85%、附图≥1000x1000px
- 类目：类目节点决定随类目必填属性（材质/功率/认证/用途等）
- 变体：需挂父子体、声明 Color 变体主题、子体库存/价格联动

【输出要求】
1. 校验摘要：回执字段错误总数、三类归口（图片/类目/变体）、字段级展开数、发布策略
2. 错误明细表：序号 / SKU / 错误类别 / 字段 / 平台要求 / 当前值 / 问题描述 / 严重度 / 修正建议 / 责任方 / 发布批次
3. 修正对照表：每条错误 → 平台要求 vs 当前值 vs 修正动作
4. 分批发布计划：无争议先发 3（图片2+类目1，AI 修正后），争议重试 3（变体3，待人工确认父子体）
5. 根因标注：引用旧 ERP 映射表，点明变体规则冲突根源；类目必须人工确认

生成后自检：42 字段错误是否三类归口完整？变体映射未确认前是否未批量发布？高风险动作是否留待人工审批？确认无误再输出。
