# M43 多租户架构设计（面向多家企业出租的 SaaS 底座）

> 本文档说明平台从「单企业 · 多部门」升级为「多企业 SaaS」的隔离与安全设计。
> 配套实现：`app/services/tenant_store.py`、`app/routers/tenants.py`、`app/core/security.py`
> （多组织映射）、`app/routers/auth.py`（品牌下发）、测试 `tests/test_m43_tenant_isolation.py`
> 与 `tests/test_m43b_tenant_sso_brand.py`。验收：`pytest` 全量零回归。

---

## 1. 背景与目标

平台早期按「一家企业 + 多部门」设计（M8–M14 的多部门隔离）。现要出租给**多家企业**，
需要一层「租户」隔离维度：

- 每家企业的私有语料 / 自建智能体 / 会话 / 审批单 **互不越界**；
- **平台级共享资产**（115 业务包 / 28 公共库 / 内置助手）**只存一份、所有租户自动可见、开通时不克隆**；
- 支持**按租户覆盖** LLM 模型、品牌（登录页/主色/Logo）、SSO（Casdoor 多组织）；
- 开通由**平台管理员**管控，与企业内部部门管理员（`dept_admin`）区分。

设计原则：共享的通用化、私有的隔离化、配置的可覆盖化——与用户「提供的数据设计成通用方式」一致。

---

## 2. 租户模型与共享资产策略

| 维度 | 取值 | 含义 |
|------|------|------|
| 平台租户占位 | `tenant_id = ""`（`PLATFORM_TENANT`） | 共享资产标记；`visible_fields` 对空 tenant 不拦截 → **对所有租户可见** |
| 企业租户 | `tenant_id = "t_" + 10位随机` | 每家企业唯一；私有数据绑该值 |
| 平台管理员 | `role = "platform_admin"` | 可跨租户看全量、可管理租户注册表 |

**共享资产（不克隆，统一升级）：**
- 115 业务包、28 公共库技能、内置通用助手 → 落库时 `tenant_id = ""`。
- 任何租户员工检索/调用都能看到，且平台升级一次全量受益。
- 企业**不能改、不能删**平台资产，只能在其之上叠加自己的私有智能体/语料。

```text
                ┌──────────────────────────────────────────┐
                │         平台共享资产 (tenant_id="")         │
                │   115 业务包 / 28 公共库 / 内置助手         │
                └──────────────────────────────────────────┘
                   ▲  ▲  ▲ 对所有租户可见（不克隆）
      ┌────────────┘  │  └────────────┐
   [租户A 私有]   [租户B 私有]     [租户C 私有]
   agent/session  agent/session     agent/session
   approval/kb    approval/kb       approval/kb
   （互不越界）    （互不越界）      （互不越界）
```

## 3. 隔离维度矩阵

| 资源 | 隔离实现 | 越界行为 |
|------|----------|----------|
| 智能体目录 | `agent_store._visible`：私有 agent 跨租户不可见；平台资产全可见；`platform_admin` 全可见 | 跨租户 404 / 不可见 |
| 调用（invoke） | `routers/invoke.py`：调用前跨租户拦截 → **404**（与「无权=不存在」统一口径） | 404 |
| 审批单 | `approval_store.pending_list(dept_id, tenant_id)`：非管理员限定本租户 | 跨租户不可见 |
| 会话 | `session_store.get_session / list_sessions`：非管理员要求 `tenant_id` 一致 | 403 / 不可见 |
| RAG 召回 | `knowledge._vis_mask` + `single_filter` 双路走 `core.filter.visible_fields`（空 tenant 全可见） | 候选阶段即剔除，不进大模型上下文 |
| 计量 / 审计 | `usage_store._visible` / `audit` 按 tenant 记录与过滤 | 跨租户不可见 |
| 文件 | `file_store` 写 `tenant_id` | 跨租户不可见 |

> RAG 跨租户召回由 `tests/test_m9_scale.py::test_cross_tenant_zero_leak` 锁定：
> 对 `t_demo` 调用者召回结果**只含** `t_demo` 文档，友商租户（`t_other`）零泄漏。

## 4. 数据模型

### 4.1 租户注册表（`tenants` 表，PG 写穿 + 内存主存）
```
tenants(tenant_id PK, name, status, config JSONB, created_at, updated_at)
```
- `status`：`pending`（刚开通）→ `active`（激活可用）。
- `config`：`{"llm":{}, "brand":{}, "sso":{}, "im":{}}` 租户级覆盖，`merged_overrides` 叠加到全局默认。

### 4.2 业务对象 tenant 绑定
- `agent_store`：`save` 默认 `tenant_id = PLATFORM_TENANT`（共享）；企业自建写 `caller.tenantId`。
- `approval_store`：`create_ticket / create_batch_ticket` 加 `tenant_id`。
- `session_store`：`create_session` 写 `caller.tenantId`。
- `knowledge`：每篇文档 `tenant_id`（平台资产为 `""`）；行级 `_ROW_TENANT` 供候选预筛。

> PG 写穿范式：`pg_store.upsert(table, key, payload)`；`_KEY_COL` 白名单须同步增表名，否则写穿静默失效。

## 5. 鉴权与网关

```text
前端 ──Bearer/OIDC──▶ 网关(Casdoor/OIDC 验签) ──X-Caller-Context(HMAC)──▶ 后端各服务
                         │                                        │
                         │  把 organization claim 翻译成 tenantId    │  只信任 X-Caller-Context
                         └────────────────────────────────────────┘  不再各自判权
```

- 调用者上下文由网关以 `X-Caller-Context` 头注入（HMAC 签名，前端不可伪造）。
- 下游服务经 `deps.get_caller` 解析，**缺失/验签失败即 401**。
- `platform_admin` 是唯一可跨租户的角色（看全量、管租户）。

---

## 6. 租户级配置覆盖（llm / brand / sso / im）

`tenant_store.merged_overrides(tid, global_defaults)` 把租户配置叠加到全局默认：
- **llm**：`model_gateway.resolve_model(tenant_id)` 优先用 `config.sso?` 实为 `config.llm.model_id`，早退返回 `{tenant_override: True}`；无覆盖回落默认/路由。
- **brand**：登录页与界面主色/名称/Logo，见第 7 节。
- **sso**：Casdoor 多组织绑定，见第 8 节。
- **im**：企业微信/钉钉连接器配置（沿用 `integrations` 既有能力）。

零配置时回落全局，行为与单租户完全一致。

## 7. 品牌下发（按租户渲染）

| 端点 | 鉴权 | 作用 |
|------|------|------|
| `GET /auth/settings` | 公开 | 返回 `platform_branding`（平台默认）+ OIDC 收口状态，供**登录前**渲染 |
| `GET /auth/branding` | 登录后 | 返回**当前租户**品牌（含平台默认回落） |
| `GET /tenants/{id}/branding` | `platform_admin` | 读取某租户品牌 |
| `PUT /tenants/{id}/branding` | `platform_admin` | 设置 `name/logo_url/primary_color/casdoor_org` |

品牌结构：`{name, logo_url, primary_color}`，未配置项回落 `DEFAULT_BRAND`（`#1677ff` 与前端 theme 主色一致）。

## 8. Casdoor 多组织映射（接 SSO）

每家企业在本平台 = 一个**租户**；在 Casdoor = 一个 **organization**。映射键：

```text
Casdoor organization  ──(id_token 的 organization claim)──▶  resolve_tenant_by_org  ──▶  tenant_id
```

- 开通租户时配置 `config.sso.casdoor_org = "<Casdoor 组织名>"`（`PUT /tenants/{id}/branding`）。
- `security.resolve_tenant_from_oidc_claims(claims)`：读 `organization/org/tenant` claim（支持数组），经
  `resolve_tenant_by_org` 得 `tenant_id`；未命中返回 `None`（回落默认，不误导）。
- **SSO 回调**（`/auth/sso/callback`、`/auth/oidc/exchange`）在验签通过后**尽力回传 `tenant_id`**，
  命中租户表才返回，供前端/网关确认落地租户。

```text
企业员工登录 → Casdoor 发 id_token(organization=acme-org)
   → 后端 resolve_tenant_from_oidc_claims → tenant_id = t_xxx
   → 网关把 tenantId 注入 X-Caller-Context → 后续请求自动按该租户隔离
```

> 这是**网关集成约定**：当前后端把 Casdoor id_token 透传作 Bearer，最终 tenant 由网关从
> organization claim 注入；上述映射函数同时供网关与「未来后端自签 token」复用，零行为变更。

## 9. 开通流程

```text
platform_admin ──POST /tenants {name, config}──▶ 状态=pending（生成 tenant_id）
      ──POST /tenants/{id}/activate──▶ 状态=active（企业可登录使用）
      ──PUT /tenants/{id}/branding──▶ 绑定 casdoor_org + 品牌
非管理员调用 /tenants 任何写操作 → 403
```

企业一激活即自动获得 115 平台共享资产，**无需克隆**。

## 10. 安全边界（已测）

- **跨租户 = 不存在**：私有资源跨租户访问统一 404，与「无权=不存在」口径一致，避免暴露"有什么"。
- **越权内容在召回阶段即剔除**：RAG 候选预筛（`_vis_mask`）先把看不见的行裁掉，不进入大模型上下文，
  不会因聚合后过滤把候选窗口吃光导致"知识库有但查不到"。
- **租户管理强隔离**：`platform_admin` 与 `dept_admin` 分级；租户注册表只有平台管理员可写。
- **品牌/SSO 配置不泄露密钥**：`integrations` 列表脱敏；`/auth/settings` 仅暴露脱敏 issuer 与平台品牌。
