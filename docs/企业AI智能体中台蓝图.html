企业 AI 智能体中台

基于开源 Agent 框架的多部门智能体协作与知识平台（私有化部署）

定位：企业统一的内部 AI 协作底座（非对外 SaaS）　|　制图日期：2026-10-31

一句话结论：把企业散落在各部门的知识与流程，沉淀成一套多部门通用的智能体协作中台， 用 Dify / LangGraph 等开源框架私有化搭建——每个部门拥有专属 AI 助手，但共用同一底座； 三大支柱是"知识分级（全域/部门/个人）+ 多 Agent 编排 + 严格权限隔离"， MVP 可在 4–6 周内落地首个试点部门。

覆盖用途：平台面向企业所有部门通用——行政、人事、销售、设计、跟单、研发、推广、财务、客服等； 每个部门都能在统一底座上拥有专属 AI 助手与知识空间（详见第 12 章场景示例）。

1. 为什么做：定位与价值

企业普遍痛点

  • 知识散落在各部门与个人，重复提问、重复造轮子
  • 制度 / SOP / 产品资料版本混乱，找得到≠用得上
  • 跨部门协作靠人工传递，效率低、易出错
  • 员工被事务性工作淹没，核心人力未释放
  • 缺乏统一 AI 入口，各部门各自买工具、数据难管控

平台价值

  • 知识资产化：制度/资料/经验进统一知识库，可问可答可复用
  • 多部门共用底座：一套平台，各部门独立空间，互不干扰
  • 交付标准化：把高频业务流程固化成可视化工作流
  • 产能放大：Agent 承担问答、初稿、分析、校对，人做判断
  • 管控可控：私有化部署、分级权限、全量审计
边界声明：本平台为企业内部通用工具，不绑定任何特定行业或业务；不对外售卖、不做多租户 SaaS（如需产品化对外，需另行评估）。所有数据私有化、不出域。

2. 总体架构蓝图

六层分层架构，自上而下：接入层 → 编排层 → 能力层 → 数据层 → 模型层 → 基础设施。多部门通过"部门空间"共用同一底座，数据按部门隔离。

3. 核心能力模块

3.1 多 Agent 协作编排 P0 重点

平台提供通用能力 Agent（所有部门可用）和部门专属 Agent（各部门自定义），由协调 Orchestrator 按任务编排协作。

Agent 角色类型输入输出核心技能
知识问答 Agent通用自然语言问题基于知识库的准确答复（含引用）RAG 检索、引用溯源
文档写作 Agent通用主题 / 模板 / 要点报告 / 方案 / 文稿初稿文档生成、模板库
数据分析 Agent通用数据 / 指标问题图表 / 洞察 / 结论表格处理、可视化、统计
流程自动化 Agent通用触发条件 / 任务跨系统执行结果连接器、API 调用
合规审核 Agent通用初稿 / 操作合规 / 质量修订建议校验规则、人工复核接口
部门专属 Agent部门自定义部门业务上下文部门专属产出部门知识库 + 专属技能
协调 Orchestrator总控任务目标拆解与派发工作流编排、状态机

3.2 技能 / 插件（MCP）体系 P1

  • 把联网检索、爬虫、表格处理、文档/PPT 生成、业务系统 API 封装成可复用"技能"
  • 采用 MCP 标准接入，便于复用开源生态插件并自行扩展
  • 部门可发布本部门的专属技能，平台统一注册与治理

3.3 企业知识库（RAG） P0

  • 全域知识库：公司制度、SOP、产品手册、公共案例、行业资料
  • 部门知识库：各部门业务知识、项目复盘、部门模板
  • 个人知识库：个人草稿、笔记、在途工作
  • 向量库选型 Qdrant（轻量、易私有化）或 Milvus（大体量）

3.4 工作流编排 P0

用 Dify 可视化工作流把高频业务流程（如"制度咨询→答复""周报生成""跨系统对账"）固化下来，新人也能一键跑通标准流程。

3.5 文档 / 内容生产 P1

  • 自动产出：分析报告、方案文档、PPT 大纲与初稿、通知/邮件草稿
  • 复用企业统一版式与语气规范，保证输出一致性

3.6 连接器 P2

  • 协同入口：企业微信 / 飞书 / 钉钉——员工在聊天里直接触发 Agent
  • 业务系统：ERP / CRM / OA / 邮件——打通数据与流程自动化

3.7 自动化 P2

  • 定时资讯抓取、报表生成、定期复盘、异常监控告警
  • 与各部门既有业务节奏联动（如周报、月结、巡检）

5. 知识库分级、关联与权限模型 P0

把"知识库链接起来"与"分级可见"合并设计：底层是三级知识库 + 权限元数据，上层通过关联机制打通检索，所有召回都按使用者权限过滤——做到"库能连、权能控、部门隔离"。

5.1 知识库三级架构

层级scope 标签内容示例可见范围维护者
全域级global公司制度、SOP、产品手册、公共案例、行业资料全员可读平台管理员
部门级department部门业务知识、项目复盘、部门模板本部门部门管理员
个人级personal个人草稿、私人笔记、在途工作仅本人本人

5.2 知识库"链接"机制（多库联邦 + 关联）

  • 多库联邦检索：Agent 可同时检索多个库，但只返回授权范围内的结果
  • 关联打通：用统一标签体系 + 实体关系（轻量关系表或 Neo4j 知识图谱）把分散条目连起来
    例：「产品手册」→ 关联 FAQ → 关联销售话术 → 关联客户案例
  • 跨库关联召回：检索时支持"沿关系链扩展"，提升答案完整性与可追溯
  • 权限即过滤：向量 metadata 带 owner_id / dept_id / scope，召回阶段即过滤，越权内容不进上下文

5.3 三级权限模型（个人 / 部门 / 全域）

角色层级可见范围典型人员操作权限
普通员工个人级自己 + 被授权内容各部门员工读个人/部门/全域公开，写个人
部门管理员部门级本部门全部 + 全域只读部门负责人增：写部门库、管理部门 Agent
平台管理员全域级全部IT / 数字化团队全部 + 权限配置 + 部门入驻

5.4 数据隔离实现

  • 行级权限：每条知识 / 文档带 (owner_id, dept_id, scope) 元数据
  • 检索过滤：查询注入用户上下文，只召回 scope 命中且归属匹配（个人 / 部门 / 全域）的内容
  • 网关拦截：RBAC 在模型网关 + API 层生效，越权调用直接拒绝
  • 审计留痕：谁在何时检索 / 导出什么，全量记录

5.5 Agent 如何遵守权限

  • Agent 调用检索工具时自动携带调用者身份上下文
  • 协调 Orchestrator 按任务把子 Agent 约束在授权范围
  • 审核 Agent 额外校验：输出不得泄露越权内容（脱敏红线）

5.6 实施建议

  • MVP 阶段先上"全域 + 个人"两级，部门级在首个试点部门落地时补齐
  • 权限元数据从第一天就打标，后期补标签成本极高

5.9 多部门治理模型

平台采用"一套底座 + 多部门独立空间"模式：所有部门共用模型网关、编排引擎与平台能力，但每个部门拥有独立的知识库、Agent 与工作流空间，数据彼此隔离。

  • 部门空间：每个部门是一个隔离空间（独立知识库 / Agent / 工作流），由部门管理员自治
  • 平台层：平台管理员负责全局模型、权限策略、技能市场与部门入驻审批
  • 跨部门协作：通过"共享空间"或 access_list 白名单，实现受控的跨域知识/流程复用
  • 治理机制：部门入驻流程、知识归属规则、合规巡检、用量与成本看板
  • 扩展性：新部门入驻只需开通空间 + 导入本部门知识，无需改动平台

5.10 部门入驻流程（流程图）

新部门接入平台采用标准化"申请 → 审批 → 开通 → 配置 → 验证 → 上线"流程，由平台管理员把控，确保数据隔离与权限正确。

说明：② 审批环节不通过则退回 ① 重新评估；⑧ 试运行通过后方可 ⑨ 正式上线并纳入治理看板。

5.11 部门入驻 SOP（行政落地版 · 纯文字分步）

本 SOP 供行政 / 平台管理员在接到部门入驻申请时按步骤执行，配套 5.10 流程图。每步标注责任人、操作动作、产出物、验收标准。

目的与适用范围：规范新部门接入平台的标准动作，确保数据隔离、权限正确、知识归口清晰。适用于所有职能部门的首次入驻与复用。

角色与职责：① 申请方 = 部门负责人 / 部门种子用户；② 审批与执行方 = 平台管理员（IT/数字化）；③ 协作方 = 行政（表单与培训）、部门管理员（本部门配置）。

Step 1 · 提交申请（申请方）
填写《部门入驻申请表》（见附录）：部门名称、业务域、拟贡献知识范围、数据敏感性自评（公开/内部/机密）、期望上线时间。提交至平台管理员。
产出：《部门入驻申请表》　验收：字段完整、敏感性自评已勾选。
Step 2 · 审批评估（平台管理员）
评估入驻必要性、数据敏感性、是否已有可复用空间。敏感数据（薪酬/财务/客户信息）需额外标注加密与机密标签要求。
产出：审批结论（通过/退回）　验收：通过进入 Step 3；退回须注明原因并通知申请方。
Step 3 · 开通空间（平台管理员）
在平台创建部门空间，生成唯一 dept_id，自动建立部门知识库（scope=department），绑定部门管理员角色占位。
产出：部门空间 + 部门知识库 + dept_id　验收：空间可见、dept_id 绑定正确。
Step 4 · 配置管理员（平台管理员）
将部门负责人（或指定人）绑定为部门管理员角色（RBAC），赋予"本部门全部 + 全域只读 + 管理部门 Agent"权限。
产出：部门管理员账号与角色　验收：该账号仅见本部门、可管理部门 Agent。
Step 5 · 知识梳理入库（部门管理员 + 种子用户）
按入库模板清洗本部门资料：制度/模板/复盘等，打标 scope=department、dept_id、tags、sensitivity。公共制度/产品手册不重复入部门库（保留全域）。
产出：已打标部门知识库首批内容　验收：每条记录含 (dept_id, scope, tags)，召回测试可命中。
Step 6 · 配置专属 Agent/工作流（平台 + 部门）
在通用 Agent 基础上，绑定本部门知识库，创建部门专属 Agent 与工作流（如 HR 招聘助手、销售话术助手）。
产出：≥1 个本部门 Agent / 工作流　验收：能基于部门知识给出准确答复。
Step 7 · 隔离与权限验证（平台 + 部门管理员）
用跨部门测试账号验证：不可见对方部门空间、不可越级看其他部门草稿、个人库仅本人可见。
产出：越权测试用例与结果　验收：全部用例通过，无越权可见。
Step 8 · 试运行与培训（行政 + 部门管理员）
部门内小范围试点 1–2 周，行政组织使用培训（问答/写作/工作流入口），收集反馈。
产出：试点反馈表 + 培训记录　验收：部门内用户可独立使用核心 Agent。
Step 9 · 正式上线与纳入治理（平台管理员）
上线公告，纳入治理看板：用量统计、成本分摊、定期合规巡检。后续知识持续由部门管理员维护。
产出：上线通知 + 治理看板条目　验收：看板可见该部门用量与权限状态。

6. 数据安全与合规 P0

保密要求

  • 全私有化部署，企业数据不出域
  • 禁用公网模型回传敏感内容（网关层拦截）
  • 部门间、项目间数据逻辑隔离

管控机制

7.1 部门级（Phase 1）多部门落地细节

MVP 已跑通"全域 + 个人"两级与首个试点部门后，Phase 1 推广到多部门，让各业务部门既能沉淀自有知识，又不破坏全域公共资产与个人草稿边界。

落地步骤

  • 开部门空间：为每个业务部门开通独立空间，绑定 dept_id，自动建部门知识库
  • 配部门管理员：RBAC 新增部门管理员角色，可见本部门全部 + 全域只读，可管理部门 Agent
  • 定沉淀规范：部门复盘 / 模板统一入部门库，公共制度/产品手册只在全域库，避免重复与版本分裂
  • 隔离验证：用跨部门账号验证不可见对方部门空间、不可越级看全域草稿
  • 部门工作流：各部门跑通本领域的多 Agent 协作闭环（如 HR 招聘助手、销售话术助手）

推荐首个试点：行政部。理由：① 知识以公开制度 / SOP 为主，敏感性低、入库快；② 问答场景全员高频，见效即被全公司看见，利于建立样板与信任；③ 不依赖业务系统对接，4–6 周 MVP 内可完整跑通，为后续部门积累标准动作与培训材料。

批次安排：第 1 批（行政、客服）打样与验证平台价值 → 第 2 批（销售、推广、HR）扩面、沉淀部门方法论 → 第 3 批（研发、跟单、财务）攻坚高难 / 高敏部门，配合系统集成与脱敏机制。

选择原则：先选"价值高 × 难度低"的部门做快速胜利（quick win），再用样板说服难度高 / 敏感度高的部门；每个试点部门均按 5.11 SOP 与 12.1 卡片推进，避免一把推开导致资源分散。

14. 给管理层的 1 页精简摘要

我们要做什么：搭建一套企业内部的 AI 智能体中台——让各部门拥有专属 AI 助手与知识库，但共用同一私有化底座，数据不出域。

为什么现在做：

  • 知识散落各部门、重复提问造轮子；跨部门靠人工传递，低效易错
  • 员工被事务性工作淹没；各部门各自买工具，数据难管控
  • 统一平台可把制度 / 资料 / 经验资产化、可问可答可复用

三大支柱：① 知识分级（全域 / 部门 / 个人）② 多 Agent 编排 ③ 严格权限隔离（员工 / 部门 / 平台三级）

投入与周期：

  • 周期：MVP 4–6 周（单试点部门）→ 多部门 2–3 月 → 智能化 3–6 月
  • 人力：平台建设组(IT) + 各部门种子用户 + 管理层 Sponsor；技术瓶颈环节可外包
  • 成本：开源框架私有化，主要成本在模型调用与 1–2 名技术人力

风险与保障：知识幻觉（严控入库 + 审核 Agent）、泄密（私有化 + RBAC + 审计）、部门配合度（管理层牵头 + 试点见效）。

建议决策：批准 ☐ 立项与预算　☐ 选定首个试点部门　☐ 排期 6 周 MVP　☐ 指定 Sponsor 与建设组。

16. 移动端（手机）操作设计

平台不止服务于坐班 PC 场景。管理层在外、销售/跟单在外勤、员工随时提问、审批待办都发生在手机上。移动端设计目标是：高频轻操作手机化、重编排留 PC、权限与安全同标准。

16.1 三种接入方式对比

接入方式适用开发成本SSO/通知推荐度
企微/钉钉/飞书 H5 / 小程序全员日常使用、免安装、与 IM 通知打通低（复用 Web App + 网页授权）天然打通首选（MVP）
独立 App（Flutter/RN）功能最全、可离线缓存、强推送中高需自接 SSO二期
微信小程序外部协作/客户场景、免登录门槛低微信授权对外场景

16.2 手机上做什么 / 不做什么（场景分级）

层级手机端（推荐）PC 端（保留）
问答与触发语音/文字问知识、一句话触发 Agent、看结果卡片复杂多轮调试
审批与待办部门入驻/共享/导出申请一键通过驳回权限策略配置

16.3 核心界面设计（手机线框图）

三块核心屏：① 工作台首页（快捷入口+待办）、② Agent 对话页（语音优先+引用来源）、③ 审批页（一键通过/驳回）。

16.4 交互设计原则

  • 语音优先：移动端默认语音输入（ASR），降低打字成本，适合外勤/驾驶场景
  • 一句话触发 Agent：自然语言指令直接映射到工作流（如"生成今日跟单日报"）
  • 卡片化结果：答案以结构化卡片 + 引用来源呈现，便于小屏阅读与转发
  • 权限可视化：每条结果标注可见范围（全域/部门/个人），避免越权困惑
  • 轻审批流：入驻/共享/导出等关键操作手机一键审批，PC 留痕

16.5 移动安全

  • SSO + 设备绑定：首次登录绑定设备，换设备需二次验证
  • 水印：敏感页面叠加"姓名+时间"水印，震慑截屏外传
  • 远程注销：离职/丢机可在后台一键擦除会话与设备登录态
  • 防截屏/复制：高敏部门（财务/HR）可选禁止截屏与复制
  • 越权防护同 PC：召回层按 scope/owner/dept 过滤，移动端不绕过

16.6 弱网与离线

  • 预缓存：部门制度/产品手册等常用知识本地预取，弱网可查
  • 断点续传：对话与任务提交在网络恢复后自动续传
  • 不存明文敏感：本地仅存脱敏摘要，敏感内容随会话结束清除

16.7 实施建议

MVP 阶段先以企微/钉钉/飞书 H5 嵌入（复用 Dify Web App，开发量最小、SSO 与通知天然打通），验证手机问答+审批闭环；二期再做独立 App（Flutter）补齐离线缓存与强推送；对外协作场景用微信小程序。所有移动端共享同一套权限与审计，不另起炉灶。

18. PC 与移动端权限一致性

平台无论通过 PC Web 还是手机 H5/App 访问，权限判定只用同一套逻辑、同一份数据，绝不因入口不同而放宽或收紧。这是避免"手机端泄密""两端看到的不一样"等问题的根本保障。

18.1 共用同一召回过滤层

PC 与移动端都调用同一个 RAG 召回服务：请求携带调用者身份（userId / deptId / role），服务在召回阶段即按 scope / owner / dept 过滤，越权片段根本不进入大模型上下文。两端没有任何"旁路"——手机端不是只读镜像，而是同一服务的不同前端。

  • 同一过滤代码：过滤逻辑只在召回服务实现一次，PC/移动共用
  • 同一元数据：每条知识带 (owner_id, dept_id, scope)，两端一致
  • 同一 RBAC：角色与策略在服务端校验，前端仅做展示

18.3 风险与纠偏

  • 风险：移动端为赶进度"临时放宽"过滤，或前端缓存越权内容
  • 纠偏：过滤器只在服务端，前端不持有越权数据；缓存仅存脱敏摘要
  • 测试：两端共用同一套越权测试用例，CI 中强制回归
  • 审计：两端操作统一进入同一审计流，出现差异可追溯到具体入口

20. 平台自动演化与自我进步机制 P1

核心结论：平台不应"上线即定型"，而应内置观测 → 评估 → 提议 → 审批 → 应用的自动演化闭环，让智能体、知识库、工作流随真实使用持续变好。关键约束：一切演化都不绕过第 18 章的"单一过滤点"，自动产出的知识 / 智能体仍受权限元数据约束，且所有自动建议必须经"人在环审批"后才生效、可灰度、可回滚。

20.1 演化闭环总图

每一次问答、每一次纠错、每一条使用数据，都回流到演化引擎；引擎评估后产出改进建议，经管理员审批、灰度发布后生效，再回到观测——形成自我进步的飞轮。

20.2 六大自演化机制

20.2.1 全链路埋点与反馈采集

每个智能体调用都记录：输入、输出、引用来源、耗时、是否命中过滤、用户评分（赞 / 踩）与自由文本纠错（"答错了 / 答不全 / 应引用某文档"）。这是演化的数据底座。

20.2.2 知识缺口探测与自生长

  • 当某类问题频繁"未找到 / 低置信"，自动标记知识缺口并建议补充文档
  • 对已接入来源（文件夹 / 数据库）按计划重新抓取，刷新过期向量，避免知识 stale
  • 新增文档自动继承来源 owner / dept / scope，不破坏分级权限

20.2.3 智能体效果评估与自优化

  • 按智能体统计：一次解决率、幻觉率、兜底率、被纠错率
  • 对提示词做自动 A/B：候选变体小流量对比，胜出者进提议队列
  • 长期低分的智能体自动打标"待优化"，推给负责人

20.2.4 工作流瓶颈与自演化

  • 识别耗时异常 / 失败率高的节点，建议加人工审核或并行
  • 某节点失败时可建议降级 / 旁路策略（保留人工兜底）
  • 高频固定流程可建议固化为模板，反哺 L1 模板中心

20.2.5 演化建议台与人在环审批

安全底线：任何自动提议默认不直灌生产。所有改进（改提示、加知识、调工作流）先进入"演化建议台"，由平台管理员 / 部门管理员确认后才生效——既享受自动演化的红利，又守住合规与可控。

20.2.6 版本化、灰度与回滚

  • 每一次生效的改动都版本化，一键回滚到上一版
  • 新版本先对单个部门灰度，无异常再全量
  • 演化动作本身进入统一审计流，可追溯到"谁审批、何时生效"

20.3 演化仪表盘（核心指标）

指标含义演化动作示例
回答一次解决率无需追问 / 纠错的占比低于阈值 → 触发提示词 A/B
知识覆盖率问题可命中权威知识的比例低 → 建议补文档 / 接新来源
越权拦截率过滤点拦下的越权尝试异常升高 → 排查配置 / 攻击
智能体健康分各智能体综合评分低分 → 标"待优化"推负责人
待审建议数演化建议台积压积压 → 提醒管理员处理

20.4 权限守恒：演化不绕过单一过滤点

自动演化产出的任何知识、智能体、工作流，在读取与生成时仍走第 18 章的同一召回过滤；新增知识自动继承 scope / owner / dept；"自动写库"接口（见 openapi.yaml 的 /kb/documents）由服务端强制回填权限元数据，前端 / 演化引擎均不可伪造。权限模型不会因"系统自动"而放松。

20.5 落地优先级与里程碑

阶段范围产出

21. 自助部门创建与业务梳理引导 P0

核心结论：很多公司存在平台管理员“事先不知道”的特殊部门（合规审计、研究院、区域合资公司、临时项目组）。 平台必须支持部门自助创建与对话式业务梳理引导，让任何部门自己把业务“长”成智能体与知识库， 且创建时自动套用第 5/13/18 章的权限模型（scope 隔离、RBAC、可见范围继承），不依赖管理员逐个手工配置。

21.1 为什么要自助建部门

  • 特殊部门普遍：合规审计部、博士后工作站、事业部下的专项组、区域合资公司、临时攻坚项目组——组织结构无法被平台预置穷尽。
  • 避免瓶颈：若每个新部门都要等平台管理员配置，平台推广会被卡在“配置产能”上，先期试点难以放大。
  • 业务主导：最懂本部门流程的是业务人自己，自助创建 + 引导式梳理比“管理员代填”更准确。

21.2 部门自助创建向导（分步）

Step 1 · 填写部门信息
部门名称、上级部门（决定可见范围继承）、业务域标签、一句话描述。提交即进入待审。
Step 2 · 选择起点
从“部门模板库”克隆一个相近模板（自带知识库/权限/示例智能体），或选“空白部门”从零搭建。
Step 3 · 系统自动初始化
自动生成知识库 scope = department:{deptId}，初始化该部门默认 RBAC 三角色（员工/部门管理员/继承平台管理员），并建立与上级的可见范围继承关系。
Step 4 · 绑定可见范围
确认本部门能看全域/本部门/个人的边界，敏感域可申请“受限共享”，需被共享方审批。
Step 5 · 提交审核生效
部门管理员（或平台管理员）一键审核，通过后该部门即出现在导航与权限矩阵中，全员可基于它建智能体。

21.3 业务流程梳理引导（对话式 + 画布）

把第 19 章的“业务梳理教练 Agent”升级为引导式画布：用多轮提问把隐性流程显性化，再自动产出可一键转构建器的草图。

  • 引导提问：这个业务的目标是什么？参与者/岗位？输入输出物？关键步骤有哪些？用到哪些系统/文件？有没有合规红线？
  • 自动产出：步骤清单 → 每步推荐节点类型（LLM 问答 / 知识检索 / 调用工具 / 人工审核）→ 生成“智能体草图草稿”。
  • 一键转化：草稿直接推送到第 19 章 L2 可视化编排器，员工补人设/知识/工具后即可发布，形成闭环。

22. 外部专业工具对接（PS / CAD 等） P0

核心结论：员工的真业务常落在专业桌面软件里。平台通过工具注册中心统一纳管三类对接方式 （API / CLI / 桌面桥），把 PS、CAD、ERP、企业网盘等变成智能体“可调用的工具”， 且所有调用不绕过第 18 章单一过滤点、走沙箱与审计。

22.1 对接原则

  • 协议无关：工具注册中心屏蔽差异，智能体只认“工具名 + 入参 + 出参”。
  • 安全隔离：本地执行走沙箱，远程调用走网关，敏感操作人工审核。
  • 权限一致：工具产出/读取的文件同样受 scope/owner/dept 约束。

22.2 三类对接方式

方式适用机制
API 对接有接口的 SaaS/系统（CRM/ERP/工单/邮件）注册 OpenAPI，网关鉴权后调用
CLI 命令行本机安装、可用命令行驱动的专业软件（PS 批处理、ffmpeg、pandoc）在沙箱内拼命令、取 stdout/文件产物
桌面桥无命令行、需进程级交互的软件（CAD 插件、PS 脚本宿主）轻量桌面客户端做本地进程桥，传参/取结果

22.3 设计类工具（Photoshop 等）对接场景

  • 批量处理：智能体生成动作/脚本，调 PS 批处理图片、导出多规格（电商图、社媒图）。
  • 素材与图层读取：读取 PSD 结构、提取图层与命名，按品牌 VI 规范自动校验尺寸/色彩/字体。
  • 出图合规：依据 VI 手册核查成品是否越界，输出“不合规点清单”供设计师修正。

22.4 工程类工具（CAD 等）对接场景

  • 图纸读取：解析 DWG/DXF，提取图元、尺寸、属性块，结构化入库。
  • 参数问答：图纸向量化 + 结构化抽取后做问答（“这个部件螺栓规格？”“净空是否满足？”）。
  • 变更比对：两版图纸 diff，生成变更清单（新增/删除/修改的构件与参数）。

22.6 安全与隔离

23. 本地文件与存储调用 P0

核心结论：员工大量知识沉淀在本地（桌面文档、设计源文件、项目文件夹）。平台通过本地文件网关（轻量桌面客户端） 与存储连接器（NAS/SMB/对象存储/企业网盘），让员工“拖进来即用、问即取”， 且文件权限映射回第 5/18 章的 scope/owner/dept，敏感操作走审批，不绕过单一过滤点。

23.1 为什么必须能调本地文件

  • 制度、报价、设计稿、项目资料多在本地/NAS，不接入则智能体“看不见”核心知识。
  • 员工希望“把这份文件交给 AI 处理”而非先手动搬运到网页，体验落差会劝退使用。

23.2 本地文件网关（桌面客户端 / Agent）

  • 授权目录：用户在电脑装轻量客户端，勾选可授权目录（桌面/项目盘/指定文件夹），未授权不触达。
  • 受控读写：智能体经授权范围读取/写入，越界一律拒绝；写/删/外发敏感文件触发审批。

25. 大模型接入与计量计费（可插拔模型 + Token 统计） P0

核心结论：平台必须回答两个问题——“用哪个大模型”与“花了多少”。 前者通过模型网关 + 适配器 + 注册表做成可插拔接口（新增模型=加适配器+一条配置，不改业务代码）； 后者通过统一计量埋点 → 用量统计 → 计费/配额形成闭环，按租户/部门/用户/智能体维度核算成本， 且不绕过第 18 章单一过滤点（用量数据同样受 scope 约束）。

25.1 为什么要把“用哪个模型”做成可插拔

  • 避免锁定：厂商与模型迭代快，业务代码不应写死某家接口，换模型不应改智能体。
  • 最优性价比：简单问答用便宜小模型、复杂推理用大模型，按任务路由降本。
  • 混合部署：公有 API 与私有化开源模型并存，敏感数据走本地模型，合规可控。

25.2 模型网关与适配器（复用第 4 章 One API / LiteLLM）

核心模式是适配器（Adapter）+ 注册表（Registry），在 One API / LiteLLM 之上做一层统一的模型抽象：

组成职责扩展方式
统一接口 ModelAdapter声明 chat / embed / rerank，及能力（流式、上下文长度、模态、价格）接口固定，长期不变
具体适配器每个模型一个实现（OpenAI 系 / Claude / 通义 / 自部署开源…）新增模型只加一个适配器类
模型注册表 Registry登记可用模型、状态、路由权重、配额热插拔：注册/停用不改业务

25.3 模型接入流程（5 步）

Step 1 · 申请 / 部署
公有模型申请 API Key 或自建额度；私有化模型完成本地部署与压测。
Step 2 · 实现 / 选用适配器
选现成适配器或实现新的 ModelAdapter（统一 chat/embed/rerank 签名）。
Step 3 · 注册到注册表
在 Registry 登记模型 ID、能力、单价、状态，平台即“可见可用”。
Step 4 · 配置路由与配额
设路由策略与部门/智能体配额，高成本模型可单独审批。
Step 5 · 灰度上线 + 监控
先小流量灰度，盯用量与质量，无异常转全量。

26. 部署运维与可观测性 P0

第 15 章给出了部署检查清单，但生产环境还需要一套运维与可观测性体系：服务挂了谁知道、慢了查哪里、数据丢了怎么恢复。本章补齐"上线后"的工程底座。

26.1 部署形态与资源规划

规模部署形态关键组件资源建议
试点 / MVP单机 Docker ComposeDify + Qdrant + PG + MinIO + 网关8C16G 起；向量库盘 ≥ 100G
多部门多机 Docker Swarm / K8s无状态服务多副本；PG 主从；Qdrant 分片16C32G×2+；独立 GPU 节点（推理）

26.2 高可用与容灾（RTO / RPO）

目标

  • RTO（恢复时间）≤ 30 分钟；RPO（数据丢失）≤ 5 分钟
  • 无单点：网关、应用、向量库均多副本
  • 数据库主从 + 自动 failover；对象存储多副本

容灾

  • 定期快照（PG / 向量库 / MinIO）
  • 异地备份保留 ≥ 30 天
  • 每季度做一次恢复演练并留存报告

26.3 可观测性三支柱

Metrics

Prometheus + Grafana。关键指标：召回延迟 P95、接口 QPS/错误率、模型调用成功率、Token 成本/分钟。

Logs

Loki / ELK 聚合全链路日志，按 tenant/dept/user 打标，便于越权排查与审计。

Traces

OpenTelemetry 串联"前端→网关→召回→模型→输出"，慢请求一键定位瓶颈。

26.4 灰度发布与回滚

  • 提示词 / 知识库 / 工作流变更走版本化，支持一键回滚
  • 新模型或新 Agent 先金丝雀小流量（如 5% 部门），观测指标无异常再全量
  • 配置错误 / 质量下降时，回滚优先于修复，止损后再排查

26.5 告警与值班

阈值示例：错误率 > 1% 持续 5 分钟、召回 P95 > 3s、模型网关 429 突增、备份任务失败。告警分级（P1/P2/P3）并对接 IM（企微/钉钉）值班群，升级路径明确。

27. AI 行为安全 P0

第 6 章覆盖"数据保密"，但企业更常遇到的是 AI 生成内容本身的风险：被诱导泄密、说错话、产出违规内容。本章建立"输入—知识—输出"三层防护，与第 18 章权限过滤互为补充。

27.1 输入侧防护

  • 提示注入检测：识别"忽略以上指令/扮演越权角色"等越狱模式，命中即拦截或降级
  • 敏感指令拦截：禁止借对话套取他人部门数据、密码、密钥
  • 输入清洗：超长截断、恶意脚本/路径遍历过滤

27.2 知识侧防护（防投毒）

  • 入库内容来源可信度校验（白名单域名 / 内部系统签名）
  • 敏感文档入库前内容审核，避免把机密误标为全域可读
  • 知识更新留痕，发现投毒可溯源到提交人并回滚

27.3 输出侧防护

内容安全

  • 违规词 / 歧视 / 违法内容过滤
  • 泄密模式检测：输出不含他人部门/个人数据片段

幻觉缓解

  • 强制引用溯源：无依据则答"无法确认"
  • 低置信度拒答或转人工
  • 关键数字 / 条款必附原文位置

越权二次防线

  • 即使召回漏过滤，输出层再校验 scope
  • 输出不含未授权可见范围内容

27.4 人工兜底与责任

高风险操作（删除/导出/对外发送）必人工确认；AI 输出不作为最终决策唯一依据，关键业务由人把关。与第 23 章本地文件、第 22 章外部工具的安全闸口一致。

32. 多租户与集团化隔离 P2

  • 隔离粒度：默认逻辑隔离（同库不同 tenant_id，召回过滤加 tenant 条件）；高敏客户可选物理隔离（独立库 / 独立部署）
  • 集团级策略统一下发，子公司可继承并局部覆盖

统一管控

资源与计费

34. 性能与成本优化 P2

规模上来后，延迟与成本会同时成为瓶颈。本章给出可落地的优化手段，并与第 25 章计量计费联动。

34.1 缓存与并发

缓存

  • 召回结果缓存（相同问题命中）
  • 热点知识 / 模型响应缓存（Redis）

并发与限流

  • 网关节流、请求队列削峰
  • 模型并发受配额约束，超限排队

34.2 模型路由降本与向量库优化

  • 按难度路由：简单任务（分类/摘要）走小模型，复杂任务才用大模型，混合推理显著降本
  • 向量库优化：索引选型（HNSW）、分片、冷热分离（高频知识常驻内存）
  • 所有优化效果在成本看板（第 25 章）可观测，形成"优化 → 计量 → 再优化"闭环

小结（v1.13 完整版图）：第 1–25 章完成"设计态"功能规划；第 26–28 章补齐上生产的硬门槛（运维可观测 / AI 行为安全 / 测试评测）；第 29–31 章决定能否被政企验收并真正用起来（审计合规 / 运营推广 / 集成架构）；第 32–34 章为规模化和合规兜底（多租户 / 法律 / 性能成本）。全平台始终复用第 5/13/18 章的权限与单一过滤模型，能力越多、边界越稳。

35. 模型选型决策框架（何时用 LLM / 传统 ML / 规则） P0

缺陷回顾（来自 AI 工程评审）：当前设计把"AI"等同于"大模型 + RAG"，缺少模型选型框架。用 LLM 做确定性、结构化、可批量的任务，会导致成本高出"几个数量级"、结果不可复现、不可解释，且引入幻觉。

35.1 外部依据

  • IBM 与企业实践共识：输入是表格/数值 → 传统 ML（XGBoost / LR）；输入是文本/多模态 → LLM。
  • 用 LLM 跑批量分类/回归，成本较传统 ML 高数倍至数十倍，且非确定性、不可解释、难审计。

35.2 选型决策树（实施核心）

35.3 落地步骤

① 建立选型决策树：按"输入类型 → 任务确定性 → 可解释性要求 → 延迟/成本预算"四问定模型类别，写入平台"新建智能体"向导，强制选型说明。
② 扩展模型网关适配器：在第 25 章注册表中新增 adapter_type ∈ {llm, ml_serving, rule}，传统 ML 与规则引擎也走同一网关，统一 caller 注入与计量。
③ 默认策略与红线：凡"确定性、结构化、可批量"的任务默认非 LLM；仅"模糊语义、生成、推理"用 LLM；关键决策引入 LLM 须人机共签（见第 33 章）。
④ 成本/质量对比看板：对同一任务并行跑 LLM 与传统 ML，记录准确率、成本、延迟，沉淀为选型知识库。

35.4 验收清单

项标准
选型决策树已上线并嵌入"新建智能体"向导，强制填写
非 LLM 接入≥ 3 个传统 ML / 规则模型接入第 25 章网关

36. RAG 质量工程（检索质量门禁） P0

缺陷回顾：当前 RAG 只做权限过滤，缺检索质量工程。纯向量检索会漏掉 30–50% 相关文档，导致答案错误/幻觉；权限过滤正确 ≠ 检索质量过关。

36.1 外部依据

  • 2025–2026 工程共识：混合检索（稀疏 + 稠密）+ 重排（cross-encoder）显著优于纯向量。
  • 先测 Recall@100 ≥ 0.95 再调重排与生成；检索质量需独立评测集与门禁。

36.2 检索管线（实施核心）

36.3 落地步骤

① 混合检索：Query 同时走 BM25（关键词/专有名词）与向量检索，按 RRF 或学习排序融合。
② 重排层：取 Top-100 候选用 cross-encoder 重排至 Top-K，提升精度。
③ 切分与元数据：采用语义切分 + 父子文档（子块检索、父块喂给模型），保留来源/章节/权限元数据。
④ 评测集与门禁：人工构建 ≥ 200 条 golden queries + 标准相关 doc_id 集合；指标 Recall@K、MRR、nDCG；CI 中跑门禁，Recall@100 < 0.95 阻断上线。
⑤ 两层过滤：检索阶段先保证"找得全"（质量层），再在第 18 章单一过滤点做"看不见"（合规层），二者解耦。

36.4 验收清单

项标准
混合检索BM25 + 向量 + 重排三件套上线
评测集≥ 200 条 golden queries，指标自动化
质量门禁Recall@100 ≥ 0.95 才放行，接入 CI
衔接：第 5 章（知识库切分/元数据）· 第 18 章（合规过滤点，质量层与合规层解耦）· 第 28/37 章（评测）。

37. ML 级评测体系（不依赖 LLM-as-judge） P0

缺陷回顾：当前评测依赖 LLM-as-judge。研究显示即便 GPT-4o，人机相关性仅 0.59–0.66，无歧义样本上反而低于人-人相关性，会"一致性地错"——自动演化飞轮若建在这之上，可能把变差的版本推上生产。

37.1 外部依据

  • ICLR 2025 与 arXiv 2025/2026：LLM-as-judge 存在系统性偏差，仅宜作辅助。
  • 正确做法：客观指标用规则校验 → 黄金集做回归基线 → 多模型交叉 + 人工抽检。

37.2 分层评测

① 客观指标（规则校验，不靠 LLM）：格式正确性、工具调用参数正确性、检索命中 doc_id 是否在区间、引用是否存在、权限越权拦截率。
② 黄金集（golden set）：人工标注 ≥ 500 条多轮对话 + 标准答案/标准动作，作为回归基线，每次改动必跑。
③ LLM-as-judge 仅辅助：若用，须多模型交叉并设校准阈值，结果只作参考不单独定生死。
④ 人工抽检 + 用户反馈：按置信度抽样人工复核；用户"踩/赞"实时回流第 20 章演化。
⑤ 评测驱动演化：第 20 章演化建议必须通过评测门禁（黄金集不退化 + 客观指标达标）才允许灰度上线。

37.3 验收清单

项标准
黄金集≥ 500 条，覆盖多轮与边界，自动化跑批
客观指标格式/工具/检索/引用/越权 5 类自动化校验
演化门禁第 20 章演化建议接评测门禁，不达标不灰度
衔接：第 20 章（自动演化）· 第 28 章（测试与评测体系）· 第 25 章（模型网关，可切换 judge 模型）。

39. 幻觉抑制与 Grounding 机制 P1

缺陷回顾：第 27 章只列了"幻觉"威胁，未给具体抑制手段。企业最怕 AI"说错话"。

39.1 落地步骤

④ 输出合规校验层：在生成后加一层规则/小模型过滤（敏感词、越权信息、违规内容）。
