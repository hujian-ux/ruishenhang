AI 工程师独立评审 · 企业内部 AI 平台蓝图 v1.14

机器学习 / 大模型解决方案 · 缺陷分析

评审对象：贵司「企业 AI 智能体中台」设计方案（34 章，含知识库分级、权限单一过滤点、模型网关、自动演化、部署运维、评测等）。评审视角：专业 AI 工程（模型选型 / 评测 / RAG / MLOps / 安全）。

核心结论：平台工程（权限、多租户、部署、计量、可插拔模型网关）做得很扎实；模型工程存在系统性盲区——把"AI"等同于"大模型+RAG+智能体"，缺三块关键能力：①模型选型框架（何时该用传统 ML / 规则而非 LLM）、②ML 级评测体系（尤其 LLM-as-judge 不可靠）、③RAG 检索质量工程（决定答案质量的第一因子）。这恰是缺专业 AI 工程经验最容易踩、且上线后最可能爆雷的地方。

二、P0 缺陷详解

P0-1 · 模型选型框架缺失（"LLM 万能"误区）

现象蓝图技术栈（Ch4）与第 19/20/25 章把一切走 LLM / Dify / LangGraph / RAG / 智能体；未区分"该用 LLM 还是传统 ML 还是规则"。 风险用 LLM 做确定性数值/分类决策（流失预测、销量预测、风控、异常检测、推荐排序）会导致：成本高出数量级、幻觉、结果不可复现、监管场景不可解释。
外部依据（已联网核验）：IBM 从业者框架与多家实践共识（2025–2026）——"输入是表格/数值、输出是数字或类别 → 传统 ML；输入是文本、输出是文本 → LLM"。用 LLM 跑几万条记录做分类，成本比专门 ML 分类器高"几个数量级"，且 LLM 非确定性、在信贷/定价/合规等需一致性的场景不可接受。来源：IBM Think "Practitioner's framework: LLM vs traditional ML"；ezitech / cognaptus 决策表；spiderhunts 模型选型对照。
修复建议：
  • 新增「模型选型决策框架」章节：把任务分为 规则引擎 / 传统 ML / LLM / 混合 / 视觉 五类。
  • 给出决策表：输入形态（表格 vs 文本 vs 图像）× 输出形态（数字/类别 vs 文本/JSON）× 确定性要求 × 合规可解释要求。
  • 默认策略：cheapest-that-works——能规则/小模型解决的绝不上大模型；"同一请求永远发最大模型"是头部团队最常犯、也最烧钱的错误。
  • 对混合流水线给出范式（如 LLM 抽取字段 → 传统模型打分决策；LLM 造标签 → 训练小分类器降本）。

P0-2 · 评测体系不达标（尤其 LLM-as-judge 不可靠）

现象第 20 章"自动演化"飞轮的"评估→优化"、第 28 章"测试与评测体系"均以 LLM-as-judge 为核心判定。 风险LLM 裁判本身偏差大、不稳定，且会"一致性地错"——自动演化可能把质量变差的版本推上生产，飞轮建立在不可靠地基上。
外部依据（已联网核验）：ICLR 2025 与 arXiv 2025–2026 多项研究一致表明——即便 GPT-4o / Llama-3.1，LLM 裁判与人类的相关系数仅 0.59–0.66；在人类高度一致的无歧义样本上，人机相关性反而低于人-人相关性（HH=1.00 时 HM 仅 0.83）；单一聚合分数（如 Krippendorff α）会掩盖系统性机器偏差；即便 Gemini-2.5-Pro / GPT-5，也在近 1/4 困难 case 上保持不了一致偏好。结论：LLM-as-judge 只能作辅助，且必须带明确 rubric + 多裁判加权。来源：Yamauchi et al. 2025（arXiv:2506.13639）；Elangovan et al. ICLR 2025；Feng et al. 2025（arXiv:2512.16041）；Li et al. 2025（arXiv:2512.01786）。
修复建议：
  • 建立黄金评测集（golden set）：人工标注、版本化、按"人类标注不确定性"分桶（高不一致样本单独看，避免虚高相关性）。
  • 建离线回归 harness：每次模型/提示词/知识库变更都跑基准，禁止"分数涨了就发布"。
  • 传统 ML 指标：precision / recall / AUC / 校准度 / 漂移；LLM 指标：任务完成率、基于检索证据的事实一致性、引用有效率、拒答率。
  • LLM-as-judge 仅作辅助：必须带 rubric、多裁判加权、且永远有"人类抽检"兜底；绝不作为唯一发布门槛。

P0-3 · RAG 检索质量工程缺失（决定答案质量的第一因子）

现象第 5 章知识库只讲"分级 + 权限 + 切片向量化"，第 18 章单一过滤点在"检索层权限"；但未定义检索质量指标、分块策略、混合检索、重排、embedding 版本化。 风险纯向量检索在技术性 / 含专名 / 精确匹配的语料会漏掉 30–50% 相关文档 → 漏召回直接造成答案错或幻觉；权限过滤正确 ≠ 检索质量过关。
外部依据（已联网核验）：2025–2026 生产共识——纯 dense 检索在技术性语料漏 30–50% 相关文档（专名、产品型号、精确匹配是典型失败场景）；必须混合检索（向量 + BM25/sparse） + 重排；且先测 Recall@100 ≥ 0.95 再调重排（重排是精度优化，修不了召回问题）；须监控 Precision@K / MRR / 引用正确率；索引、embedding、重排器、提示词、模型、评测集全部要版本化；并做 grounding 校验（答案是否只用检索来源）。来源：stackpulsar "Multi-Dimensional AI Retrieval 2026"；Buffer/Kovalenko "Testing RAG Systems" 2025；nerdleveltech "Common RAG Failures"；CSDN 智能体社区实操清单。
修复建议：
  • 补「RAG 质量工程」章节：混合检索（向量+BM25）、重排模型（cross-encoder）、语义分块（按段落/章节，约 200–500 token）。
  • 设检索 SLO：Recall@100 ≥ 0.95、MRR、Precision@K、引用正确率@K；按主题/部门持续监控。
  • Embedding 选型与版本化：明确模型、维度、中文能力；更换模型必须全量重建索引。
  • 强制 grounding：答案须对应检索片段并带引用（标题/时间/来源）；材料不足即拒答。
  • 检索日志全量留存 + 失败样本回放，定位问题卡在哪一环（检索 vs 生成）。

三、P1 缺陷详解

P1-4 · 非 LLM 模型的 MLOps 缺失

贵司明确要"机器学习模型解决方案"，但蓝图 Ch26 部署只讲基础设施，无任何模型生命周期：训练流水线、特征存储、模型注册/版本化、漂移监控、重训触发器、模型 A/B。若真要做流失预测/销量预测/异常检测，这些必须补齐。

修复：新增 MLOps 章节（特征→训练→注册→监控→重训→灰度），与 Ch25 计量、Ch26 部署打通。

P1-5 · 幻觉 / grounding 无具体机制

Ch27 列了"提示注入/越狱/投毒/合规"等威胁，但缓解只写"输出内容合规校验"一笔带过。缺：引用强制、置信度/拒答、约束解码（JSON/function calling 可靠性）、不确定性校准。

修复：落地 grounding 三件套（强制引用 + 拒答阈值 + 约束解码），作为 Ch27 的落地细则。

P1-6 · 成本/延迟缺路由与语义缓存

Ch25 计量与 Ch34 性能是"两张皮"。无按任务复杂度路由（简单→小模型）、无语义缓存（最大成本杠杆）、无流式/SLO。单网关无路由 = 成本与延迟同时失控。

修复：在模型网关加路由层 + 语义缓存；定义延迟/成本 SLO（P95/P99、每次对话 token）。

P1-7 · 模型质量可观测性缺失

Ch25 统一计量只记 token/成本，不记质量：用户点赞/踩、任务成功率、幻觉事件、转人工率、每智能体质量分。"无法度量就无法改进"。

修复：在计量层叠加"质量遥测"，与 Ch20 演化飞轮共用采集层。

四、P2 缺陷详解

P2-8 · 无优雅降级 / 人工升级路径

智能体可能静默失败；无"置信度低于阈值→转人工"、无"LLM→规则"回退级联。若 P0-2 评测弱，自动演化会把坏版本推上线且无兜底。

修复：定义降级/升级策略（每智能体配 fallback 与人工接管点），与 Ch19 L3 人工审核节点联动。

P2-9 · 中文语言特化不足

贵司在东莞、面向中文企业。embedding/LLM 需中文优化；中文 token 计数口径与英文不同；多语言/方言处理未明确。检索与评测集都应中文优先。

修复：明确"中文优先模型 + 中文评测集 + 中文 token 计费口径"，纳入 Ch25/Ch28。

P2-10 · Agent / 工具层安全未闭环

单一过滤点在检索层（Ch18/27）。但工具调用（Ch22）、智能体互调（Ch19 L3）、外部 API 可外泄数据或代表用户执行越权动作。无沙箱出口防火墙、无工具输出清洗、无角色级动作白名单。

修复：把安全闭环从"检索层"延伸到"工具/动作层"——沙箱出口管控、工具输出脱敏、角色级动作 allowlist。

五、已做对的地方（保持，勿回退）

  • 权限三级 + 单一过滤点（Ch5/Ch13/Ch18）：全域/部门/个人分级 + 召回阶段统一过滤，是正确且少见的扎实设计，务必保留。
  • 可插拔模型网关 + 适配器 + 注册表（Ch25）：加模型=加适配器+一条配置，业务零改动——架构正确。
  • 计量埋点与计费配额（Ch25）：方向对，只需叠加"质量遥测"（P1-7）。
  • 自动演化飞轮（Ch20）：方向前瞻，但地基（评测，P0-2）必须先补，否则飞轮会转错方向。
  • 多租户/集团化、部署运维、审计合规（Ch26/29/32）：生产化三件套已齐，优于多数内部平台方案。

七、上线前检查清单（可直接用）

  • 每个智能体都标注了"为何用 LLM 而非规则/传统 ML"，且附有选型决策表依据
  • 存在版本化、人工标注的 golden set，并按人类标注不确定性分桶评估
  • LLM-as-judge 仅作辅助，发布门槛含人类抽检，绝不单凭裁判分数
  • 检索 Recall@100 ≥ 0.95、MRR / Precision@K / 引用正确率 有持续监控告警
  • 采用混合检索（向量+BM25）+ 重排；embedding 模型与索引版本化
  • 答案强制带引用、材料不足即拒答（grounding 三件套落地）
  • 存在非 LLM 模型时，有训练/特征/注册/漂移/重训的 MLOps 链路
  • 模型网关有任务复杂度路由 + 语义缓存 + 延迟/成本 SLO
  • 质量遥测（成功率/幻觉率/转人工率）与计量埋点同源
  • 每个智能体有降级/人工升级路径，不静默失败
  • 中文模型优先、中文评测集、中文 token 计费口径已明确
  • 安全闭环覆盖检索层 + 工具/动作层（沙箱出口、输出脱敏、角色级 allowlist）
