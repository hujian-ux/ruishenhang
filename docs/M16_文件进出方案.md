# M16 · 文件进出（P0）

> 一句话：把「上传 xlsx → 按技能包执行 → 下载产出 xlsx」这条链路打通。
> 技能包的本质是**表格进、表格出**，而 M15 结束时 invoke 只吃 `input: str`，
> 20 列的台账根本进不来——这是 115 个技能包能不能真用的最后一个硬门槛。

---

## 一、为什么必须先做这个（缺口实证）

M15 把 115 个技能包装进了平台，但真实业务动作跑不起来：

| 现象 | 根因 | 后果 |
|---|---|---|
| 用户没地方传费用台账 | `POST /agent/invoke` 只接受 `input: str` | 技能包的「输入契约」要求的 xlsx 进不来 |
| 就算硬塞文本也跑不动 | 5000 行 × 20 列全塞 prompt 会打爆上下文且烧钱 | 大表无法处理 |
| 跑完只有一段文字 | 没有产出物通道 | 用户拿不到能交上去的文件 |
| 产出无处存放 | 对象存储只服务知识库文档 | 无文件生命周期与权限 |

M16 补的正是这四件。

---

## 二、链路

```
① 上传   POST /agent/files  (multipart)
         ├─ 校验类型/大小（20MB，xlsx/xlsm/csv/tsv/txt/md/json）
         ├─ sha256 去重（同人同文件复用记录，不在对象存储堆副本）
         ├─ 落对象存储：agent-files/{dept}/{file_id}/{name}
         └─ 立即解析 → 回结构预览（表头/列画像/前 20 行）

② 执行   POST /agent/invoke  { agent_id, input, file_ids:[...] }
         ├─ 校验附件可见性（越权与不存在统一 404，防枚举）
         ├─ tabular.to_prompt_context  → 列画像 + 样本行（预算内）
         ├─ agent_runtime.run_agent(..., file_context)
         │    └─ 技能包 system_prompt（M15）+ 附件上下文 + 任务输入
         └─ artifact.build_xlsx(answer) → 产出物 xlsx → 对象存储 → 注册表

③ 下载   GET /agent/files/{file_id}
         └─ 后端代理回字节流（带鉴权 + Content-Disposition 中文名）
```

---

## 三、五个关键设计决策

### 1. 上传即解析，而不是执行时才解析

用户传完立刻知道「识别到 5 行 × 6 列，表头是科目/数量/单价/金额/上月金额/同比」。
如果表里有合并单元格或双层表头导致识别错位，此刻就能发现并重传，
而不是等执行完拿到一份胡说八道的结果再回头找原因。

解析失败（损坏文件、加密文件、未知格式）**不拒收**：文件照常入库，
但 `meta.parse_ok=false` + 原因回给前端；执行时上下文里会写「附件不可用，
请说明无法读取并列出需要补充的字段，不要臆造数据」。比整个请求 500 有用。

### 2. 进 prompt 的是「列画像 + 样本」，不是整表

这是全链路最关键的取舍。`tabular` 对每个 sheet 抽取：

- **列画像**：列名、类型（number/date/text/empty）、空值率、唯一值数、取值样例
- **样本行**：前 80 行（可读的 markdown 表）
- **行数声明**：明确告诉模型「以上为样本，实际共 N 行」

总预算 7000 字符。模型判断业务问题靠的是「有哪些列、什么类型、有没有异常」，
不是看完每一行；真要逐行核算的，提示里给了「如需逐行请说明取数口径」的退路。

**表头识别不是取第一行**：真实台账第一行常是「2026年6月费用台账」这种标题。
`_header_row` 在**前 5 行**里挑「非空单元格最多且以文本为主」的那行当表头，
其余行并入数据或丢弃。这一条不做，后面所有列名都会错位一格。

### 3. 产出物永远存在

`artifact.build_xlsx` 无论模型输出什么都会生成文件：

| sheet | 内容 | 必要性 |
|---|---|---|
| 执行结论 | 技能包名/输入文件/模型/执行时间/run_id/trace_id/引用知识 + 答案正文 | 必生成。没有它，「下载产出物」按钮会时有时无，用户无法预期 |
| 各产出表 | 答案里的 markdown 表格、` ```json ` 数组 → 各自一个 sheet，sheet 名取表前最近的小标题（`## 二、明细表` → 「明细表」） | 技能包的产出契约就是出表 |
| 输入数据摘要 | 文件名/工作表/行数/列数/列名（类型） | 可溯源：对着结果能核对吃的是哪份数据 |
| 输入数据（可选） | 单 sheet 且行数 ≤2000 时附原始数据 | 方便复算，但多 sheet/大表不附，避免产出物变成输入副本 |

表头样式：工业蓝 `#1F4E79` 白字、冻结首行、按内容估列宽（中文按 2 字符宽），
打开即能看，不用再手动调格式。

### 4. 下载走后端代理，不用预签名直链

预签名 URL 要把 MinIO 端口暴露给浏览器、还要配 CORS；内网部署场景里
前端根本不知道 MinIO 地址。文件 ≤20MB，代理流式回传完全够用，
而且鉴权与 RBAC 保持在同一条链路上。

**不区分「不存在」与「无权」**，统一 404 —— 否则可以靠枚举 file_id 探测
别人传了什么。

### 5. RBAC 沿用第18章，不另起一套

platform_admin 全量 / dept_admin 本部门 / 员工本人。
文件比知识文档更敏感，所以**不设 global**：部门管理员也看不到别部门的文件。
上传件的删除仅限本人（平台管理员可代删）。

## 四、接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/agent/files` | 上传（multipart），回 `file_id` + 结构预览 |
| GET | `/agent/files` | 可见文件列表，`kind=upload\|artifact`、可按 `run_id` 精确定位 |
| GET | `/agent/files/stats` | 文件量与字节数 + 对象存储是否在线 |
| GET | `/agent/files/{file_id}` | 下载原件/产出物（后端代理，带鉴权） |
| GET | `/agent/files/{file_id}/preview` | 表格结构预览 |
| DELETE | `/agent/files/{file_id}` | 删除（仅上传者本人或平台管理员） |
| POST | `/agent/invoke` | 新增 `file_ids`，响应新增 `run_id` / `files_used` / `artifacts` |

`/agent/invoke` 响应新增字段：

```json
{
  "run_id": "run_77a42237dd5c",
  "files_used": [{ "file_id": "...", "filename": "管理费用明细.xlsx",
                   "parse_ok": true, "sheets": 1, "rows": 5 }],
  "artifacts": [{ "file_id": "art_...", "filename": "费用异常波动分析_管理费用明细_20261103-2209.xlsx",
                  "size": 7414, "download_url": "/api/v1/agent/files/art_..." }]
}
```

## 五、存储与持久化

| 层 | 存什么 | 不可用时 |
|---|---|---|
| 对象存储（MinIO，S3 协议） | 文件字节流 `agent-files/{dept}/{file_id}/{name}` | 内存兜底（`memory://`），链路仍通 |
| PG `agent_files` 表（jsonb） | 元信息（owner/dept/object_key/sha256/run_id/meta） | 仅内存生效，重启后产出物丢失 |
| 内存 `file_store._FILES` | 全量元信息（主存） | — |

**顺手修掉的两个旧 bug**（都是「看起来做了、实际没生效」这类）：

1. `pg_store._KEY_COL` 白名单里没有 `agents` —— M15 建了表、`save()` 也调了
   `upsert`，但被白名单静默拒绝，**「智能体写穿 PG」实际只落内存，重启 115 个包全丢**。
   已补 `agents` / `agent_files`，并加测试 `test_persist_tables_registered_in_whitelist`
   做回归护栏。
2. `invoke` 里的 `audit.record("generate", ...)` 写在 `return` **之后**，是不可达代码
   —— M13 的「生成」审计事件从未落库。M13 单测直接调 `audit.record` 因此没暴露。
   已移到 return 前，并顺带把 `run_id`/附件/产出物写进审计 meta。

## 七、诚实的边界（P0 没解决的）

1. **纯 CPU + 无 LiteLLM 时走 stub**：答案是对上下文的回显，产出物的
   「执行结论」正文不好看。接真模型（`LITELLM_BASE_URL`）后正常。
   stub 是既有的降级路径，不是 M16 引入的问题。
2. **不做公式复算**：xlsx 里的公式按 `data_only=True` 读缓存值；如果文件是
   「刚生成还没被 Excel 算过」的，数值可能为空。要算公式得引入 LibreOffice 无头转换。
3. **不处理合并单元格**：合并表头会被读成「首格有值、其余为空」，
   表头可能出现 `col3/col4` 这种补位名。真实双层表头的台账需要人工确认一次。
4. **不进索引**：附件的表格不写入知识库，属于「一次性输入」。要沉淀成知识仍需走 `/kb/documents`。
5. **产出物只支持表格**：不做 docx/pptx 产出。技能包若要出报告文档，属 P1。

## 八、下一步（P1）

1. **真模型端到端**：接 LiteLLM 后拿「费用异常波动分析」「报销单合规预审」两个包
   跑真数据，看模型是否真按技能包的流程与产出契约出表（当前只验证了链路，没验证效果）。
2. **166 个 xlsx 交付物做 few-shot**：方案库里已有这些产出样例，塞进 prompt 能让
   模型照着格式产出，比只说「出个表」稳得多。
3. **合并单元格识别**：把双层表头拍平成 `父列_子列`，解决第 3 条边界。
4. **公式复算**：LibreOffice 无头转换兜底。
5. **多轮附件**：当前每轮附件独立，跨轮引用同一份台账要重复上传（虽有 sha256 去重，
   但仍是用户操作）。可在会话级做「附件上下文」。
