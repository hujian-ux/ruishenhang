02平台侧的 4 个真缺口（都做了实证，不是推测）

缺口实证后果
提示词无处安放 注册后落库字段只有 agent_id/name/adapter_type/scope/status，连 description 都丢了 115 个包全变成同一个默认助手，行为一样
运行时写死提示词 agent_runtime.SYSTEM_PROMPT 是模块级常量，run_agent 只拿 agent_id 查状态 就算存进去也不生效
智能体只在内存 _AGENTS: dict = {}，无 PG 写穿 重启 115 个包全蒸发
批量导入不可治理 每次注册都开一张审批单 115 张单淹没审批台，人工无法逐条看
另有一条不该改的设计：未发布的智能体 invoke 返回 403（第35章红线）。这条不为批量导入放宽， 而是给批量导入一张「批次单」—— 红线照旧，只是可治理。

03融合链路（已跑通）

skill.md→ 解析：剥序号 + 别名归一→ POST /agents/import→ 1 张批次审批单→ 整批 published→ 按各自 system_prompt 执行
调用时按该技能包自己的「角色 → 适用场景 → 输入契约 → 工作流程 → 产出契约 → 硬规则」执行； 计量照常落账、审计照常留痕。96 个判为纯生成（输入由用户给），19 个判为 RAG 类（确实要查制度库）。

05质量分层：不是 115 个都能直接上生产

梯度数量说明
结构齐（4 项信号以上）40有流程有契约，可先拿去做真模型试点
补规则后可用61缺硬规则，跑起来容易「说得好听、落不了地」
需人工重写14缺流程也缺契约
两个必须说清的事实： ① HR 20 个被判 usable 不是质量差 —— 它的流程写在「作业手册原文」里、没单列章节，结构信号抓不到；抽样读下来 HR 是办公类里最实的。 ② 硬规则只有 17/115 —— 这是最该补的一项。技能包的价值恰恰是「不让你说空话」，而平台的价值主张是「可审计、可复核」。没有硬规则的包，跑出来仍是漂亮废话。

06还差什么（按优先级）

优先级事项为什么
P0 文件进出 技能包的本质是 xlsx 进、xlsx 出。现在 /agent/invoke 只吃 input: str，费用台账里那 20 列数据根本进不来。需加 input_files（复用已有 MinIO）+ 产出物写回 + 下载链接。
P1 166 个 xlsx 交付物做 few-shot 每个方案都带「原始数据 + 交付物」成对样例，这是最好的 few-shot。塞进 system_prompt 后输出会从「看起来对」变成「格式真的对」，性价比最高。
P1 补硬规则（17/115） 优先补办公 62 个：每个补 3–5 条可判定红线，如「分母必须写明」「无记录不得估算」「问题必须落到唯一责任人+时限」。
P2 审批台折叠批次单 批次单含 115 个 agent_ids，需折叠展示 + 整批通过/驳回按钮。

先补文件进出（P0）→ 拿「经营复盘」+「报销单合规预审」两个包做真模型端到端试点 → 再铺开 115 个。
