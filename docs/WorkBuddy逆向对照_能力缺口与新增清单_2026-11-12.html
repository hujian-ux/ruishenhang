01结论：我们缺的不是功能，是运行时工程

先把判断说清楚，后面 38 行矩阵只是这个判断的证据展开。

一句话：WorkBuddy 强在「运行时工程」——流式会话、可中断、可插话、进程预热、工具沙箱、可靠投递、automations 调度、插件生态；我们强在「企业治理」——多租户、配额、审批、评测、203 技能包、MLOps、产物生成。所以该补的是运行时那一层，而不是把它的功能清单抄一遍。

三条判断依据

  1. 我们的 9 项「已覆盖」全在治理与知识侧，13 项「缺失」里 10 项落在同一根脊柱上：会话运行时 → 工具循环 → 执行边界 → 记忆 → 调度投递。这不是五个功能，是一条链。
  2. 我们已有骨架、但执行是「虚」的：workflows.py 有 4 类节点编排，但 llm 节点是 "mode":"dry_run" 占位（backend/app/services/workflows.py:231）；agent_runtime.py 记录 tool_calls 但从不真正执行（:380 / :415）；events.py 有订阅总线但没有 outbox、租约与退避。这三处「有壳无核」是投入产出比最高的补齐点。
  3. 它最强的那几条恰恰有合规雷：设备指纹 qimei36、Turing 风控令牌、aegis 遥测被它自己的合规评审定为 P0（30-compliance/COMPLIANCE-RISK-REVIEW.md R01–R03 / R12）；keyblob 自标「静态可解密」。这些属于「看得懂但不学」。
一个反直觉的提醒：如果按「WorkBuddy 有 68 个 CLI 命令、7 个市场源、101 个插件」来排期，我们会做出一堆用不上的东西。它是桌面单机产品，冷启动、离线、插件分发是它的生存问题；我们是企业 B/S 中台，这些问题多数不存在（见 §7 不照搬）。真正要补的只有「会话—工具—边界—记忆—调度」这条链，加上飞书连接器与 MCP 服务端暴露这两个企业集成硬需求。

04P0：五项，决定试点「能不能用起来」

排序依据不是「WorkBuddy 有」，而是「没有它，试点用户第一周就会放弃」。五项构成一条链，必须按序做。

P0-1会话流式化：SSE + 中断 + 状态机≈ 6 人日
补的是
矩阵 A-1 / A-2 / A-3（缺失）
为什么
今天 /agent/invoke 是同步返回，长答案要等整段生成完；用户点「停」没有语义，只能刷新页面丢上下文。这是体验断崖，也是所有后续能力（工具循环、轮次回滚）的前置。
怎么做
新增 POST /agent/stream（text/event-stream），事件族对齐逆向的最小集：response_started / output_text_delta / tool_call / tool_result / response_done / error；每次请求发一个 request_id，前端按 protocolRequestIds 同思路映射回包；DELETE /agent/stream/{request_id} 做 cancel；前端 Chat.tsx 接 AbortController + 增量渲染。旧的同步端点保留，兼容小程序与外部调用方。
关键约束
取消必须真正停掉上游 LLM 流（关闭 httpx stream），不能只断前端；落库在 response_done 时统一写，取消的轮次要标记 cancelled 而不是丢弃。
验收
① 2000 字回答首字节 < 1.5s；② 生成中点停止，后端日志显示上游连接已关闭，会话 turns 状态为 cancelled；③ 断网重连后会话可续；④ 旧同步端点回归测试全绿。
P0-2通用工具调用循环（tool registry + 多轮 tool_calls）≈ 10 人日
补的是
矩阵 B-9 / B-10（缺失 / 部分）
为什么
agent_runtime.py 今天只把 tool_calls 记进返回体（:380 / :415），模型说了要查东西、我们并不会去查——「智能体」在客户眼里就退化成「带 RAG 的问答」。这一项不补，Builder 里的 tool 节点、MCP 工具、审批流都只是摆设。
怎么做
① 建工具注册表：name / schema / 权限级别 / 是否需要审批 / 执行器，首批接 web_search、kb_search、mcp_tools、artifact_write；② agent_runtime 改成真循环：think → tool → observe 最多 N 轮（默认 6，可配），每轮工具调用必须过 guardrails.guard_tool_call()（已有 :555），高危工具转 /approval 挂起；③ 流式下把 tool_call/tool_result 作为 SSE 事件回传前端展示。
关键约束
循环上限必须硬性，防 token 爆炸；工具异常要作为 observe 内容回灌而不是中断整轮；每次工具调用落审计。
验收
① 「先搜一下最新政策再回答」能观测到 2 轮以上 tool_call 且答案引用了搜索结果；② 触发审批类工具时对话挂起、审批通过后续跑；③ 单轮 token 成本与耗时在 /usage 可见；④ 工具失败注入测试不 panic。
P0-3工具执行沙箱边界≈ 8 人日
补的是
矩阵 E-30（缺失）
为什么
一旦 P0-2 让模型能真执行工具，风险等级立刻从「说错话」升到「动文件 / 出网 / 读凭据」。先把边界立起来再放工具，否则就是在客户环境里裸奔。
怎么做
① 工作区白名单：每个 Agent 声明可访问目录，执行前 isInsideRoot 校验（对齐逆向 13-security R3 的自定义协议教训）；② 规则文件外置 sandbox_rules.json，default=ask，凭据类目录三态硬禁（.ssh / .gnupg / .env* / *.key 的 read=deny|write=deny|delete=deny，不允许用户降级）；③ 命令执行走白名单命令 + 超时 + 输出截断；④ 高危动作强制走审批，不提供「跳过审批」开关（逆向 --dangerously-skip-permissions 是明令反例）。
验收
① 路径逃逸测试集（../、绝对路径、符号链接、UNC、%TEMP% 绕行）全部拒绝；② 凭据目录读写删一律 deny 且不可配置覆盖；③ 规则命中 ask 时审批单里能看到完整命令与目标路径。
P0-4跨会话长期记忆≈ 6 人日
补的是
矩阵 A-8（缺失）
为什么
用户第二周再进来，系统对他一无所知——这是「智能体」和「聊天窗」最直接的体感差异。投入最小、感知最强的一项。
怎么做
① 表 memory_facts（scope=user/tenant/agent、key、value、source_turn、confidence、created_at、deleted_at）；② 写入时机：显式指令（「记住…」）优先，其次靠每轮结束的抽取器（低频、异步、可关）；③ 注入：会话开始按 scope 取 top-K 拼进 system 段，带来源标注；④ 管理面：Identity 页加「记忆」tab，可查看 / 编辑 / 删除 / 关闭自动抽取。
关键约束
不做成人格文件那种纯文本堆叠（我们是多租户，需要按租户隔离与可审计）；记忆写入必须可追溯来源轮次，可单条撤销。
验收
① 会话 A 说「我们公司报销用 XX 系统」，新开会话 B 问报销流程，答案能引用该事实；② 用户在管理面删除后，新会话不再出现；③ 跨租户不串（同 key 不同 tenant 隔离测试）。
P0-5任务调度 + 可靠投递≈ 12 人日
补的是
矩阵 D-24 / D-25 / D-26（全部缺失）
为什么
客户对中台的第一个付费理由通常是「每天 8 点把日报发我群里」，我们现在连一个可用的定时器都没有。而且这不是加个 cron 就完事——投递失败静默丢失比不做更糟。
怎么做
① 表 automations（schedule_type / cron 或 rrule / timezone / valid_from / valid_until / enabled / owner）+ automation_runs + automation_delivery_outbox；② 调度用 APScheduler（AsyncIOScheduler）或 celery beat，对齐逆向参数：tickMs / missedWindowMs（错过窗口内补跑）/ concurrency；③ 投递走 outbox：先落库再发，指数退避 + 最大重试 + 死信标记，复用现有 events.py 订阅与 im_gateway 发送；④ 运行记录对账：终态回收孤儿 running、崩溃后 restorePersistedQueuedRuns 同思路恢复。
关键约束
单实例部署也要防重（DB 行锁或 SELECT … FOR UPDATE SKIP LOCKED）；时区必须显式存 UTC 存、本地算；valid_until 到期自动停，不要留着半夜还在跑。
验收
① 配一个每 5 分钟的定时任务，连续 12 次运行记录齐全；② 停掉 IM 端点再恢复，验证失败 3 次后重试成功且 outbox 无残留；③ 调度进程 kill -9 后重启，排队中的 run 自动续跑；④ 前端能看运行历史和失败原因。
P0 的执行顺序不能换：P0-1（流式）→ P0-2（工具循环）→ P0-3（沙箱）→ P0-4（记忆）→ P0-5（调度）。理由：P0-2 的事件要挂在 P0-1 的 SSE 上；P0-3 必须在 P0-2 真正放权给模型之前就位；P0-4/P0-5 复用 P0-1 的会话与 P0-2 的工具执行入口。P0-3 若滞后，等于先开门后装锁。

10与本次对照无关、但会被顺手问到的三个欠账

写在这里避免下一轮又被重新发现。均来自本轮实测，不属 WorkBuddy 对照范畴。

  • 配置假通：根 .env 里的 TAVILY_API_KEY / BOCHA_API_KEY 本地运行不生效——_load_env_files() 只读 backend/.env 与 backend/.env.local。实测这两个键为空、WEB_SEARCH_PROVIDER=auto，即联网检索实际在走免费 HTML 抓取。
  • 语料空转：corpus_inbox 12 个文件里 8 个是 PLACE_FILES_HERE.txt 占位，仅财务 2 个技能各 1 对 xlsx；SEED_DEMO_CORPUS=True 使「真语料灌库」验收无法成立（readiness() 实测 real_corpus=not_configured）。
  • MLOps 空跑：pipeline_status() 各阶段 done=True 但 done_all=False、trained=False、models_registered=0、datasets=0、runs=0——是「形状齐了、没跑过」的状态。

另有一条安全项：LLM key 明文落在 backend/.env.local，且此前明文出现过的硅基流动 / 博查 key 尚未轮换。这与 §7 的 keyblob 判断同源，建议在 P1-1 做凭据加密时一并处理。
