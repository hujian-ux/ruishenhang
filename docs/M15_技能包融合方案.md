## 一、一句话结论

**能融，而且已经融进去了——但不是"把 115 个包复制进平台"那么简单。**

技能包是 `prompt-as-skill`（一套执行手册），而平台原来的智能体只有一个"名字 + 类型 + 状态"，
**装不下技能包的灵魂（提示词）**。所以先补齐 4 个平台缺口，再批量导入；
现在 115 个包已全部进平台、按行业/职能分类、统一受审批红线与计量审计管辖，
**审批通过即可按各自的流程独立执行**。

## 三、平台侧的 4 个真实缺口（都做了实证，不是推测）

融合前我用真实接口试了一次"把一个技能包当普通智能体注册"，结果暴露出四个硬缺口：

| # | 缺口 | 实证 | 影响 |
|---|---|---|---|
| 1 | **提示词无处安放** | 注册后落库字段只有 `agent_id/name/adapter_type/knowledge_scope/model_id/registered_by/dept_id/status`，`description` 都丢了 | 115 个包全都会变成同一个"平台默认知识助手"，行为完全一样 |
| 2 | **运行时写死提示词** | `agent_runtime.SYSTEM_PROMPT` 是模块级常量，`run_agent(agent_id, ...)` 只拿 agent_id 查状态，不读提示词 | 就算存进去也不生效 |
| 3 | **智能体只在内存** | `routers/agents.py` 的 `_AGENTS: dict = {}`，没有 PG 写穿 | 重启 115 个包全蒸发 |
| 4 | **批量导入不可治理** | 每个注册都 `create_ticket` 开一张审批单 | 115 张单淹没审批台，人工不可能逐条看 |

> 另有一处"设计如此、不算缺口"的行为：未发布的智能体 invoke 返回 403（第35章红线）。
> 这条**不该为批量导入放宽**，否则红线就形同虚设。做法是给批量导入一张"批次单"。

## 四、M15 已落地（代码 + 测试 + 契约）

### 4.1 打通链路

```
skill.md
  │ 解析（章节别名归一 / 序号剥离 / 未识别段落保留）
  ▼
AgentDefinition  system_prompt = 角色 → 适用场景 → 输入契约 → 工作流程 → 产出契约 → 硬规则 → 通用红线
  │
  ├─ adapter 判定：96 个 llm（输入由用户给，纯生成）
  │                19 个 llm_retrieval（合同条款确认/制度问答/FAQ/合规材料包…确实要查库）
  ▼
POST /agents/import  （默认 batch_approval=true → 一张批次审批单）
  ▼
agent_store（内存 + PG 写穿，重启不清零）
  │  状态 pending_review
  ▼
POST /approval/{id}/decide  一次决策 → 整批 published
  ▼
POST /agent/invoke → agent_runtime 按该 agent 的 system_prompt 执行（skill_applied=true）
  ▼
计量落账（M7）+ 审计留痕（M13）
```

## 五、质量分层：不是 115 个都能直接上生产

用结构信号（流程/输入/产出/规则/公式）分级，**这只是"结构是否齐"的客观指标，不等于内容好坏**：

| 梯度 | 数量 | 说明 |
|---|---|---|
| 结构齐（4 项信号以上） | 40 | 有流程有契约，可直接试点 |
| 补规则后可用 | 61 | 缺硬规则，跑起来容易"说得好听、落不了地" |
| 需人工重写 | 14 | 缺流程也缺契约 |

**两个必须说清的事实：**

1. **HR 20 个被判"usable"不是质量差**，而是它的流程写在"作业手册原文"里、没单列"工作流程"章节，结构信号抓不到。抽样读下来 HR 是办公类里最实的（中位 1408 字，面试评估汇总 3635 字）。
2. **硬规则只有 17/115**。这是最该补的一项 —— 技能包的价值恰恰是"不让你说空话"，
   而平台的价值主张是"可审计、可复核"。没有硬规则的包，跑出来仍是漂亮废话。

> 我一开始用"正文字数 < 600 = 模板壳"分级，实测是**误判**：
> 被判最薄的「费用异常波动分析」（247 字）其实含 4 步流程 + 量价分离公式，是可用的。
> 已改用结构信号，并把这次纠错记录在脚本注释里，避免后人再按字数判断。

## 六、还差的三件事（按优先级）

### P0 — 文件进出（技能包的本质是 xlsx 进、xlsx 出）

现状：`/agent/invoke` 只吃 `input: str`，返回 answer 文本。
而技能包的输入契约几乎都是"费用台账.xlsx / 五份部门报表 / 库存清单"，
产出也是"交付物.xlsx"。**只靠粘贴文本，xlsx 里那 20 列数据根本进不来。**

需要：
- `AgentInvokeRequest` 加 `input_files: [doc_id]`，复用已有 MinIO + kb 原文读取能力
- 产出物解析为结构化结果 → 写回对象存储 → 返回 `download_url`
- 前端 Skills 页支持直接上传文件

### P1 — 把 166 个 xlsx 交付物样例变成 few-shot

每个方案目录都带"原始数据 + 交付物"成对样例。这是**最好的 few-shot 素材**：
把同一技能的"原始数据 → 交付物"作为示例塞进 system_prompt，
模型输出会立刻从"看起来对"变成"格式真的对"。这是性价比最高的一步。

### P1 — 补硬规则（当前只有 17/115）

优先补"办公角色"这 62 个（用户实际要用的场景）：
每个包补 3–5 条可判定红线，比如"分母必须写明""无记录不得估算""问题必须落到唯一责任人+时限"。
我可以按板块批量生成初稿，你抽检确认。

### P2 — 前端审批台支持批次单

现在审批台展示的是单张单，批次单有 115 个 agent_ids，需要折叠展示 + "整批通过/整批驳回"按钮。
