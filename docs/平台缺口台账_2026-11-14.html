Platform Gap Audit

企业智能平台 · 缺口与收口台账

不是能力盘点，而是收口盘点。平台该有的骨架已经长齐，问题集中在三处：改动没有落地成版本、能力没有接到入口、系统没有对着真依赖跑起来。

基线 f49cb4b（2026-11-11） 取证时间 2026-11-14 22:28 取证方式 实跑测试 / 构建 / 端口探测 / 代码对读 缺口 24 项

一句话结论

平台不缺功能，缺收口。今天代码里 27 个路由、64 个服务、185 个 API 路径、1102 个测试全绿、前端可正常构建，能力面是完整的；但有 104 个文件躺在工作区没提交、4 类能力没有前端入口或没有配置、4 个外部依赖全部连不上——也就是说，现在这套东西「能跑测试」但「不能交付」。

最该先做的不是加功能，而是把已有的东西钉进版本、接上入口、对着真依赖跑一遍。否则再写 10 个模块，也还是这个状态。

8 项 · 每一处都可能让用户误判系统能力
C1

「试跑工作流」按钮调的是 dry_run，真执行在另一个端点

P0
现状PlatformOps.tsx:400 的「建并试跑工作流」调 api.runWorkflow → POST /builder/workflows/{wid}/run，该路由在 workflows.py:233 固定返回 "mode":"dry_run"。真正的执行是 /execute（run_workflow_real():404）与 /execute-stream（arun_workflow_stream():463）。
影响用户在界面上点「试跑」看到的是编排校验结果，不是模型真的跑了一遍。这会系统性地让人高估工作流的完成度——是本轮最危险的一处。
动作：前端改调 /execute-stream 并展示真实节点输出；或保留 dry_run 但把按钮文案改成「校验编排」，并另给一个「真跑」。两者不要共用一个按钮文案。

三段推进顺序

先让改动落地，再让系统真跑，最后才谈能力补齐

第一段 · 收口约 3 天 · 覆盖 P0 中的 5 项

  • 拆 3–5 个语义提交推远端，等 CI 全绿（A1 + A2）——这是唯一「不做则其余全部无效」的动作
  • 起 Docker 四件套，跑写入→重启→读回，验证持久化（D1）
  • 跑四个验收脚本，把 llm_key / search_key 从 configured_unverified 推到 verified（C7）
  • 前端改调 /execute 或拆开两个按钮文案，让「试跑」名副其实（C1）

第二段 · 真跑约 1 周 · 涉及外部资源，需要业务配合

  • 选 1–2 个真实部门灌 50+ 份文档，关 SEED_DEMO_CORPUS，出带来源的回答样本（D2 + B6）
  • 补调度器页面（B1）与记忆 / 工具回放（B2）——把已有的能力变成看得见的能力
  • 接 OIDC 测试 IdP + 1 个 MCP server（B5）
  • 三处占位降级改为 503，不再返回看起来像结果的假结果（C3）

第三段 · 交付化约 1 周 · 可以并行

  • 清理 6 个无用服务、统一 feast 仓库、删已取代实现（C5 + C6）
  • 备份定时化 + 一次恢复演练 + 告警接飞书出口（E1 + E2）
