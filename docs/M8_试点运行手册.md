# M8 试点运行手册（两周 · 一个部门）

> 一句话：M8 把平台从「能演示」推到「能跑两周」——语料能批量灌且重启不丢、召回能出基线并每天复测、成本能出曲线和外推。手册本身就是试点的操作脚本。

## 0. 这次到底补了什么

| 能力 | M7 之前 | M8 |
| --- | --- | --- |
| 语料导入 | UI 单篇上传，500 篇手点 500 次 | `ingest_corpus.py` 目录批量导入，43 篇/秒，出失败清单 |
| 去重 | 无，重复文件会稀释召回 | 内容指纹 sha256 去重，重跑整批 0 新增 |
| 重启 | 知识库在内存，重启即清空 | PG `kb_documents` 载回，250 篇重启后仍是 250 篇 |
| 索引重建 | 每篇一次全量重建（500 篇=分钟级等待） | 批量写入只重建一次 |
| 召回评测 | 只能跑内置 golden（18 篇演示语料） | 外部 golden（只写 query + 标题），出 JSON/Markdown 报告 + 漂移历史 |
| 成本 | 只有聚合表 | 逐日曲线（空白日补 0）+ 月累计 + 月末外推 + 预算水位 |
| 看板 | 无 | 试点看板：语料规模 / 召回 / 成本 一屏 |

## 1. 前置条件（不满足就别开跑）

1. **底座在位**：PG 5432、对象存储 9000、LiteLLM 4000。
   ```powershell
   cd D:\enterprise-ai-platform\backend
   .\scripts\start_m6_stack.cmd -SkipValidate
   ```
2. **关掉演示语料**：`SEED_DEMO_CORPUS=0`。不关的话 18 篇演示文档会跟真实文档抢排名，指标是假的。
3. **准备语料目录**：`.txt / .md / .csv / .json / .log / .yml / .sql / .html`。PDF/Word 先转文本（本模块不塞解析重依赖）。
4. **圈定权限边界**（这一步最容易翻车）：哪些进 `department`（本部门可见）、哪些只能 `personal`（仅本人）、哪些要 `global`（全员，仅平台管理员可写）。
5. **配额与预算**：`USAGE_QUOTA_TOKENS`（默认 200 万 / 30 天）、`USAGE_MONTHLY_BUDGET_CNY`（默认 500）。

## 2. 三个命令

```bash
cd D:/enterprise-ai-platform/backend

# ① 导入（先干跑看清单，再真跑）
./.venv/Scripts/python.exe scripts/ingest_corpus.py --dir D:/corpus/sales --dry-run
./.venv/Scripts/python.exe scripts/ingest_corpus.py --dir D:/corpus/sales --scope department --dept d_sales

# ② 基线（每天跑一次，追加到漂移历史）
./.venv/Scripts/python.exe scripts/eval_baseline.py --golden D:/corpus/golden.jsonl --gate

# ③ 底座（PG/对象存储/网关）
./scripts/start_m6_stack.cmd -SkipValidate
```

试点模式启动后端（记得带开关）：

```bash
SEED_DEMO_CORPUS=0 ./.venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8080
```

导入报告落 `backend/reports/ingest_report.{json,md}`；基线报告落 `backend/reports/baseline.{json,md}` + `history.jsonl`（漂移）+ `latest.json`（看板读它）。

## 3. golden 怎么写（决定评测有没有意义）

只写 `query` + `expected_title`，doc_id 由系统反查：

```jsonl
# 每行一条，# 开头为注释
{"query": "满 199 减多少", "expected_title": "五一营销活动方案 v3"}
{"query": "报销什么时候截止", "expected_title": "财务报销流程", "scope": "global"}
```

写 golden 的三条纪律：

1. **从真实提问里抄**，不要从文档标题反推。用标题反推的 query 天然容易命中，指标会虚高。
2. **目标文档必须唯一**：`expected_title` 找不到时会被计入 `dropped` 并写明原因（不静默丢弃）。
3. **50 条起步，100 条封顶**：少于 50 条方差太大；超过 100 条边际收益低。

## 4. 指标口径（争论时按这张表对齐）

| 指标 | 定义 | 为什么看它 |
| --- | --- | --- |
| Recall@100 | 目标文档是否进前 100 个可见结果 | 第36章 CI 门禁（≥ 0.95）；低于它就是"根本捞不到" |
| Recall@10 | 目标文档是否进前 10 | 决定喂给 LLM 的上下文够不够 |
| MRR@10 | 目标文档排名的倒数均值 | 衡量"排得靠不靠前"，同类文档多时会掉 |
| nDCG@10 | 位置加权的相关性 | MRR 的平滑版，避免单条命中拉高 |
| filter_accuracy | 越权文档是否一条都没进结果 | 第18章红线，必须 1.0（语料无越权样本时不算失败，报告会标注探针数） |
| 月末外推 | 本月已发生 + 近 7 日均 × 剩余天数 | 回答"这套东西一个月烧多少钱"，比单价表可信 |
| 配额水位 | 部门滚动 30 天 token / 上限 | 超 100% 时调用直接 429（真拦，不是告警） |

## 5. 两周时间表

| 阶段 | 动作 | 判据 |
| --- | --- | --- |
| D1 上午 | 圈语料 + 权限边界，`--dry-run` 看清单 | 清单里没有不该进的文档 |
| D1 下午 | 真导入，看 `ingest_report.md` 的失败清单 | added ≥ 200；failed 逐条有解释 |
| D2 | 写 50–100 条 golden，跑基线 | Recall@100 ≥ 0.95 |
| D3–D4 | 部门真实使用，每天看板 10 分钟 | 有调用、无 5xx、无 429 |
| D5 | 加 30–50 篇新语料，重跑基线 | 召回不塌（见第 8 节实测） |
| D6–D9 | 继续用；把答得差的 20 个问题记下来 | 形成"补语料清单" |
| D10 | 出结论：召回、人均成本、TOP20 问题、扩不扩 | 一页结论 + 决策 |

## 6. 每日 10 分钟检查清单

打开「试点看板（M8）」，从上到下看三件事，看板上没有的再点进对应页：

| # | 看什么 | 正常 | 异常动作 |
| --- | --- | --- | --- |
| 1 | 语料篇数 | 与昨天比只增不减 | 掉了 → 查 PG 是否重启丢数据 |
| 2 | Recall@100 | ≥ 0.95 且不持续下滑 | 下滑 → 补 golden 覆盖的语料，别改 golden 去凑 |
| 3 | 本月成本 / 外推 | 外推 ≤ 预算 | 超预算 → 模型管理页停高价模型，或收紧配额 |
| 4 | 活跃 / 空白日 | 工作日都有调用 | 空白 → 问部门是不是没用起来（产品问题，不是技术问题） |
| 5 | 调用明细里的"真生成"占比 | 接近 100% | 掉下来 → LiteLLM 网关挂了，在走 stub |
| 6 | 会话列表 | 有人真的连续追问 | 全是一轮就断 → 对话体验有问题 |

## 7. 异常处置

| 现象 | 根因 | 处置 |
| --- | --- | --- |
| 导入报告 failed 一堆"无法解码" | 文件是 GBK 之外的编码 / 二进制 | 转成 UTF-8 再导；图片 PDF 先 OCR |
| 重跑导入 added 不为 0 | 语料被编辑过（内容变了，指纹就变了） | 正常现象；变异版本会作为新文档入库，需人工清理旧版 |
| 召回率突然掉 | 新语料和旧语料高度重复（同一制度多个版本） | 用内容去重 + 人工删旧版；同主题多版本会互相顶掉 |
| 重启后语料变少 | PG 不可达，退化成纯内存 | 看 `/kb/stats` 的 `pg_available`；先修 PG 再重启 |
| 调用返回 429 | 部门配额超限 | 提配额或降调用量；429 是真拦截，不是提示 |
| 看板「基线」显示"未评测" | 还没跑过 baseline | 跑一次 `eval_baseline.py`，或点看板按钮（需管理员） |
| 成本曲线全是 0 | 窗口内没有调用 | 检查是不是所有人都只用 stub；或窗口设太短 |

## 8. 本机实测数据（2026-11-02，模拟语料 250 篇）

用 `gen_pilot_corpus.py` 生成 220 篇 + 30 篇增补（8 个主题族），验证链路而非业务质量：

| 时点 | 语料 | 子块 | golden | Recall@5 | Recall@10 | Recall@100 | MRR@10 | 门禁 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| D1（220 篇） | 220 | 2686 | 44 | 0.6364 | 0.8864 | 1.0 | 0.3489 | 通过 |
| D5（+30 篇） | 250 | 3052 | 44 | 0.5909 | 0.8864 | 1.0 | 0.3388 | 通过 |

读法：**"捞得到"没变（Recall@100 = 1.0）**，但"排得靠前"略降（MRR 0.3489 → 0.3388，Recall@5 掉了 4.5 个点）。这正是加语料后的正常代价——同类文档变多，目标文档在候选里被挤低一位。要盯的是这个缓降斜率，不是单次绝对值。

其他实测：

- 导入 220 篇耗时 **5.1 秒（43 篇/秒）**，重跑整批 220 篇全部判重、**78 ms**。
- 基线 44 条 × 250 篇语料耗时 **6.6 秒**；200 条约 30 秒（可接受，CI 只用 18 篇演示语料）。
- 重启后端后 `/kb/stats` 仍是 220 篇（PG 载回生效）。
- 语料增长 13.6% 后 Recall@10 未下降 → "加语料不塌"这条在本规模成立。

> 注意：MRR@10 = 0.35 偏低是**真实结果**而非 bug——模拟语料里有 28 篇标题同构的"XX大区渠道政策"，目标文档常排在同类中间。真实业务里同类制度并存时也会这样，这正是需要父子切分 + 重排继续调的地方。

## 9. 扩到第二个部门的前置条件

1. 第一个部门跑满两周，Recall@100 ≥ 0.95 且连续 5 天不下滑；
2. 人均月成本可接受（外推 ≤ 预算的 60%，留余量给第二个部门）；
3. `filter_accuracy = 1.0` 且跨部门探针数 > 0（说明真的在多部门语料下验证过）；
4. 有一个部门能自己写 golden（不然每次评测都得平台同学代劳，不可持续）。

## 10. 已知边界（不要在评审时被问倒）

- **检索索引在内存**：Qdrant 只接了建集合的壳，250 篇没问题，2000 篇以上要真接 Qdrant 并做增量索引。
- **对象存储可降级**：MinIO 不可达时原文落内存，重启会丢原文（元数据在 PG 还在），试点期要求 MinIO 常开。
- **PG 单点**：没有主从，生产要补备份；`kb_documents` 的 `content` 列存全文，2000 篇以上建议只存对象存储 key。
- **personal scope 召回弱**：个人文档只有 1 篇时，泛化 query 召回率很低（实测 0.14），个人知识库要做"本人加权"。
- **评测集是资产**：golden 改动要走 Git 评审，不能为了过门禁去改 golden。
